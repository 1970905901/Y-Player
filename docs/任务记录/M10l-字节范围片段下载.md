# M10l 字节范围片段的下载（`#EXT-X-BYTERANGE`）

- 状态：**已实现**（本地静态闸门全绿 + 新单测；Mac 编译 / 测试待 YG）
- 时间：2026-10-10
- 触发：M10c 的「留口」第二条 —— 字节范围片段以前**如实拒绝**（「这条清单按字节范围取片段
  （#EXT-X-BYTERANGE），本平台暂不支持下载」）。这类清单里多个片段**共用同一条 URI**、
  靠字节范围区分；不认它要么全拒、要么「同一个文件下 N 遍」，两种都糟。

## 一、做法

1. **解析时就定死每一段的范围**（`HLSManifest.SegmentRange` + `segmentRanges`，与 `segments` 一一对应）：
   `#EXT-X-BYTERANGE:<n>[@<o>]` 的 `n` 与 `o`；**`o` 缺省时按 RFC 8216 接上一段的结尾**——
   所以解析器要跟踪 `lastRangeEnd`，这段知识不该让下载器再推一遍（同 M10k 的 IV 口径）。
2. **`o` 推不出来的清单整份拒绝**（第一段就没写 `@offset`）：`hasUnresolvableRange` 标出来，
   `refusalReason` 说「不合 RFC 8216 的写法，不敢猜着下」——猜错的后果是拼出一个错位的文件，还看不出来。
3. **下载器发 `Range`**（`DownloadRunner.fetch(_:task:range:)`）：`Range: bytes=o-(o+n-1)`，
   两个硬检查 —— **必须是 206**（返回 200 = 上游忽略 Range，回来的多半是整段文件）、
   **回来的字节数必须等于 n**；任一不对就报错（拼错了看不出来）。
4. **与加密片段可叠加**：每片先按范围取、再按需解密 —— 两次处理互相独立（顺序上先取后解）。

## 二、口径与取舍

- **`Range` 头走既有的请求头通道**：与站点 header 合并（`task.headers` 里本来就有 `Referer` 这类），
  `Range` 只是多一条；下载鉴权不受影响；
- **不做「按范围并发取同一文件的不同段」**：仍是顺序取、顺序追加（M10d 的既定做法）；
- **进度按实际收到的字节数算**：范围片段的 `Content-Length` 就是范围长度，能对上。

## 三、故意没做

- 多段 Range（`bytes=0-9,20-29`）：HLS 不会这么写；
- 与「加密 + 范围」组合的专门用例：两条路径独立（先取后解），没有互相影响的地方；
- 断点续下：仍与 M10d 一样「失败从头下」。

## 四、验证点（Mac）

1. `swift test --package-path Packages/CatVodCore`：解析两条新用例 ——
   按片段存 offset / length（含缺 offset 接上一段尾部）、第一段就没 offset → 整份不可下；
2. `swift test --package-path Packages/CatVodSource`：下载器端到端 —— 假 transport 按 `Range` 切片回 206，
   断言三段拼回整份文件、且 `Range` 头依次是 `bytes=0-15` / `bytes=16-31` / `bytes=32-63`；
3. 全包测试 + App 编译照旧（**没有新文件**）；
4. **上机**：找一个带 `#EXT-X-BYTERANGE` 的源下一集 —— 以前立刻失败，现在应能下完并本地播。

## 五、教训（写给下一次）

- 「同一份知识放哪一层」在 M10k（IV）和这里（范围起点）是同一个答案：**能在解析时定死的，
  就别留给下游推** —— 下游只有「第几片」，推法一旦不全（比如漏了 init 片不吃序号）就是错位；
- 「如实拒绝」的清单要有**具体理由**：`refusalReason` 从「不支持字节范围」变成「缺起始偏移」——
  前者过时了，后者才是真的下不了的原因。
