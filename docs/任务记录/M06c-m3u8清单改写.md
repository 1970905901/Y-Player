# M06c HLS 清单改写（`/m3u8` 路由 + 清单自动选端点）

- 状态：已推送（CI 结果见「验证记录」）
- 时间：2026-10-07
- 范围：M6 第三步 —— 把上游 `server/process/M3u8.java` 那条路由补齐，并让**播放侧真正用上它**
- 前置：M06a（本地服务 + `/proxy`）、M06b（播放侧接线）

## 一、为什么这条路由是非要不可的

M06b 把播放资源改走 `/proxy?url=…&h=…`，只解决了**主请求**的 header 注入。
HLS 的链路是「主清单 → 子清单 → 分片 / 密钥」：播放器请求主清单时地址被我们换成了本机，
但**主清单正文里的子清单 / 分片地址仍是上游原文** —— 播放器会直接向上游取它们，
站点 header 又丢了（典型表现：主清单 200，第一个分片 403）。

上游的做法是在本机提供一个 `/m3u8` 路由：取到清单后把里面**所有**地址（含 `URI="…"`）改写回本机，
于是每一跳都经过本机、都能注入 header，而且相对路径有了正确的基准地址。

## 三、逐条对齐（上游 `M3u8.java` → 本仓库）

| 上游 | 本仓库 |
| --- | --- |
| `isPlaylist(url, contentType)`：MIME 含 `mpegurl`/`m3u8`，或去掉 query 后以 `.m3u8`/`.m3u` 结尾 | `HLSPlaylistRewriter.isPlaylist`（同一判定） |
| `looksLikePlaylist(text)`：去空白后 `#EXTM3U` 开头 | 同名方法 |
| 非注释行 → `proxy(resolve(base, line))` | `rewrite` 里同一分支（`resolve` 等价 `HttpUrl.resolve`） |
| `URI="([^"]+)"` 逐个替换（`#EXT-X-KEY`/`MAP`/`MEDIA`） | 手工扫描替换（语义相同，少一处正则依赖；引号不闭合时不猜） |
| 分片/密钥走同一路由原样转发 | `passthrough(_:request:)`（状态码与 header 照搬） |
| 响应头 `no-cache`、`Content-Type: application/vnd.apple.mpegurl` | `playlistResponse(_:body:)`（并额外去掉 `Content-Encoding`） |

## 四、设计取舍（与上游的差别，逐条记录）

1. **代理地址用客户端连过来的 `Host`**，不硬编码 `127.0.0.1:9978`：本项目端口是扫出来的
   （9978–9998），写死会在第二个实例上指错。
2. **`h`（注入 header）逐跳带下去**：上游那条路用的是写死的 UA/Referer，而我们的 header 来自站点配置，
   逐跳丢失会让分片 403。
3. **重算 `Content-Length`、去掉 `Content-Encoding`**：正文是重新拼的，长度必须重算；
   上游的 gzip 已被 `URLSession` 解掉，留着会让播放器按压缩体解析。
4. **清单必须走 `/m3u8` 而不是 `/proxy`**：只有 `/m3u8` 会继续改写下一层；这条选择收在
   `LocalProxyURLBuilder.path(forMediaURL:)` 里，UI 只调用一次。
5. **行分隔原样保留**（上游 `String.split` 会吃掉结尾空行）。

## 五、明确未做

1. **流式转发**：仍是缓冲式（> 32MB 明确 502）；落地临时文件 + `HTTPBodySequence(file:range:)` 未做。
2. ~~**`hlsRules` 的消费点**~~ → 已在 **M06d** 完成（信号制清理器 + `/m3u8` 接线）。
   顺带查出当时的模型**形状就是错的**：上游这个字段是规则包形态（`HlsAdRule`），
   按 `{hosts, regex, exclude}` 建模会让真配置里的规则静默失效 —— 已在 M06d 一并修正
   （那条形状属于解析规则 `SniffRule`，它的 `exclude` 另有用途）。
3. **代理会话池 / `doh` / `hosts` 覆盖**：与 M06b 同一批未做。
4. **`/m3u8` 只做清单改写**：不做广告插播识别（上游也没有）。
