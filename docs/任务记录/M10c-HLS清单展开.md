# M10c HLS 清单展开（要下哪些地址）

- 状态：主清单 / 媒体清单 / fMP4 init 片 / 加密与字节范围标记全部落地，11 条单测；
  **分片下载与落盘编排未做**（下一步）
- 时间：2026-10-09
- 依赖：M10a / M10b；不依赖传输层（纯文本 → 地址列表）

## 一、为什么单独切这一层

离线下载要先回答「到底要下哪些地址」。答案全在清单文本里，而这一步的坑**错了都不报错**，
只会下出一堆没用的文件：

| 坑 | 不处理的后果 |
| --- | --- |
| 相对地址（`seg-1.ts`、`/v/seg-1.ts`、`../shared/x.ts`） | 下到拼接错的地址（自己拼字符串必错，所以用 `URL(string:relativeTo:)`） |
| `#EXT-X-MAP`（fMP4 的 init 片） | 漏了它，后面的片段是解不出来的裸流 —— 文件下完了但**播不了** |
| `#EXT-X-KEY`（`METHOD=AES-128`） | 存下一堆密文，用户以为「下载坏了」 |
| `#EXT-X-BYTERANGE` | 多个片段**共用同一个 URI**、靠范围区分 —— 不认它会「同一个文件下 N 遍」 |

所以规则写在这个纯逻辑层里，并由单测逐条钉住；后两个**不支持就如实标出来**
（`isDownloadable = false`），沿用本平台一贯的做法：不支持的要说清楚，不猜、不静默产出垃圾。

## 二、规则

- **主清单**（`#EXT-X-STREAM-INF`）：收集变体（地址 + `BANDWIDTH`）；
  ``HLSManifest/bestVariant`` 取**带宽最高**的那条，全都没有带宽字段时取清单里的**第一条**
  （比较器是严格递增，并列时保留靠前的）；
- **媒体清单**（`#EXTINF`）：按顺序列出片段地址（绝对化）+ 时长求和（只用于展示）；
- **非清单**：返回空结果（`hasContent == false`），调用方据此当**普通文件**直下 ——
  这样「直链 mp4」和「HLS」走同一条下载流程，不必在调用方分叉。

## 三、下一步（清单）

1. **`DownloadRunner`**：拉播放地址 → 是清单就展开 → 逐片下载并追加写进同一个文件 →
   用 M10a 的 ``DownloadQueue`` 规则推进任务状态（进度按累计字节，总量未知时留 `nil`）；
2. **本地地址接管**：已下载的集在详情页改成播本地文件；
3. **界面**：详情页的下载按钮 + 「下载管理」的任务列表。

## 四、留口

- 加密片段（AES-128 / SAMPLE-AES）：要自研解密（拿 `#EXT-X-KEY` 的 URI 取密钥 + AES-CBC 解），
  暂时如实拒绝~~ → **AES-128 已在 M10k 支持**（取 key + AES-CBC 解 + 缺省 IV 按媒体序号推）；SAMPLE-AES 仍如实拒绝；
- 字节范围片段：要支持得发 `Range` 请求再按范围合并，同上先拒绝；
- 主清单选择目前只按带宽（下载场景够用）；若以后要「按用户选的清晰度」，把选择权交给调用方即可
  （`variants` 已经是完整列表）。
