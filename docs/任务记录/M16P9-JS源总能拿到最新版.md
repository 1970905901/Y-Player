# M16P9 js2p 接口「导入之后还是旧版本」

- 状态：**已修**（本地静态闸门全绿 + 新单测；真机由 YG 用 Mac 验证）
- 时间：2026-10-09
- 现象：用户填 `https://9280.kstore.vip/ceshi/index.js.md5`，加载后拿到的是**8 月 1 日那一版**
- 上游实测（本机 curl，2026-10-09）：

```
GET /ceshi/index.js.md5  → 200, 32 B,  内容 35dcc10d533153dbb94298792664ad04
GET /ceshi/index.js      → 200, 6291879 B, MD5 = 35dcc10d533153dbb94298792664ad04
两个响应都带 Cache-Control: no-cache（不是 CDN 缓存的问题）
```

也就是说**服务端是对的**（摘要与内容一致），卡住的是我们这边。两条根因：

## 根因一：「源缓存时间」把 `.md5` 增量校验整个跳过了

`SourceRepository.loadCached(configURL:maxAge:)` 里，JS 源命中有效期内缓存时**直接返回本地**
（原注释还明确写着「JS 源也不请求 `.md5` 摘要」）。可选值里有 **「永不」** ——
选了它就永远不校验、永远停在旧 bundle 上；反过来讲，把 6 MB 的 bundle 和 32 字节的摘要
放在同一个「有效期」里，本身就是把上游给的增量更新机制作废了。

**修法**：JS 源在这个函数里**一律不给结论**（返回 nil），交给 `load(configURL:forceRefresh:)`
那条带 `.md5` 校验的路 —— 摘要一致仍然直接命中本地、**不重下 bundle**；拿不到摘要（离线 / 上游挂）
才退回已校验过的缓存。参考实现（webhtv `NodeBundle`）本来就是每次都拉那个摘要、超时 3 秒。

## 根因二：换了 bundle 不重启宿主，站点清单还是内存里的旧代码

`AppModel.refreshHost` 里的 `js2pHost ?? JS2PHostService(...)` —— 宿主已经起来时**复用**它，
`service.sites(forceRestartHost:)` 里那个 `forceRestart` 平时是 false（只有「强制刷新」才 true），
而 `JS2PHostService` 用的是**同一份配置**（`scriptURL` 固定）。于是：

- bundle 在磁盘上被换成新版了，但**跑着的 node 已经执行过旧代码**，站点清单在内存里 →
  界面还是旧版本（磁盘上是新的，摘要也是新的，只有眼睛看到的是旧的）；
- 顺带修掉同族问题：**换 JS 源**（另一个 `index.js`）时也复用旧宿主 → 站点清单永远来自上一个接口。

**修法**：两处判断 ——
1. 宿主的 `runtimeConfiguration.scriptURL` 与本次要跑的不一致 → 停掉、重建宿主；
2. 本次加载**真的重下了 bundle**（`LoadedSource.usedCache == false`）→
   `forceRestartHost: true` 重启一次（内存里的旧代码不重启不会自己重读文件）。

## 界面文案

设置 → 数据 → 缓存的说明补一句：**js2p 接口例外，每次加载只拉几十字节的 `.md5`**，
变了才重下 bundle —— 免得用户以为「源缓存时间」对 JS 源也意味着「不联网」。

## 故意没做

- 没有给 JS 源的摘要请求加「多久才查一次」的节流：参考实现就是每次查（32 字节、3 秒超时），
  加了节流又要引入一个新状态，收益不抵复杂度；
- 没有把「缓存太旧」做成 UI 上的红色告警：摘要一致本来就是正常命中，旧不旧由上游决定。

## 验证点（Mac）

1. 先记下「设置 → 源地址 → 摘要」现在是哪一串；
2. 点**「加载」**（不用「强制刷新」）：旧构建下摘要不变、站点清单不变；修好后应当——
   摘要变成 `35dcc10d…`（= 上游当前值，可用上面的 curl 自己核），站点清单也换成新版；
3. 在同一台机器上换到另一个 js2p 源再加载：站点清单必须立刻换成新源的（不复用旧宿主）；
4. 断网后点「加载」：应回退到本地已校验过的缓存并给出告警，而不是白屏或报错崩掉。
