# M04P9 真会话（视频闭环）—— 解码线程 + 背压 + 自动开播

- 状态：**已实现**（本地静态闸门全绿 + 新单测；Mac 编译与测试待 YG）
- 时间：2026-10-10
- 触发：M04P8 把「帧 → 显示」的三块基础设施立起来后，这一步把它们和
  `LibavInput` / `LibavVideoDecoder` 串成**一条能跑的视频闭环**：
  打开 → demux → VT 硬解 → 显示层。

## 一、做法（`LibavFFmpegSession`）

- **专用解码线程**（`Thread`，QoS `userInitiated`）：解码是阻塞式 C 调用，不占协作线程池；
- **背压**：每轮先问渲染器 `isReadyForMoreMediaData`，吃不下就 5ms 后再来 ——
  显示层排满了就不硬解，内存不会被帧堆爆；
- **攒一帧再喂**：一帧的显示时长要等**下一帧的 pts** 才知道，所以先攥着 pending，
  下一帧到了再发；EOF 时 `drain()` 收尾（硬解与 B 帧都会在解码器里留几帧），
  末帧用最近一次间隔兜底；
- **自动开播**：第一帧**真的排上**之后才 `play()` + 报 `.playing`
  （在此之前界面那边还是 loading —— 「命令下了」和「有画面了」不是一回事）；
- **进度事件**：时间轴变化 ≥0.25s 才报一次 `time`，不做逐帧刷屏；
- **close 纪律**：先置停，等解码线程自己退出（最多 200ms）**再**释放 input/decoder ——
  没有 interrupt callback 之前，不能释放线程可能正在读的上下文；幂等。

接线口径：`FFmpegSessionFactory.make(surface:)` —— **没给画面层就返回 nil**
（同 MPV：宁可说不可用，也不给没有画面的播放器）；引擎生产入口加 `videoSurface`。

## 二、这一版的边界（不假装，接线前必须补齐）

| 缺什么 | 现在的行为 |
| --- | --- |
| 音频 | `setVolume` / 音频轨道选择是空操作（M04P10） |
| seek | 空操作，不假装动了；`startPosition` 被忽略 |
| 软解 | `decoderMode == .software` 直接拒绝并说清楚 |
| 网络卡读 | `close()` 不保证立刻收线程（会等，超时就让它自然收尾） |
| 逐帧统计 | `stats()` 是打开时的快照（分辨率/编码/容器/硬解），不是 mpv 那种实时属性 |

**所以 `FFmpegAvailability.isEngineImplemented` 仍是 false、协调器仍不创建它** ——
音频与 seek 补齐、上机验证能播之后才接线。

## 三、故意没做

- 音频解码与输出（M04P10：swresample + `AVSampleBufferAudioRenderer`，挂同一条 synchronizer）；
- seek / 起点续播（下一个独立片：`av_seek_frame` + 解码器 flush + 显示层清队）；
- UI 接线（`FFmpegVideoView` + PlaybackView 分支）—— 等能用再上界面，不做没人用的空壳。

## 五、续记（2026-10-10，首轮 Mac 编译）

红在 `convenience`：**类的 designated init 不能 `self.init` 委派** ——
MpvEngine 那套「生产 init 委派到注入 init」的写法能成立是因为它是 **actor**，
照搬到类上就是编译错误。`init(surface:)` 标 `convenience` 即解。
