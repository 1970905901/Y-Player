# M25P1 下载列表：状态与进度是真的

- 状态：**已实现**（Store 读路径与恢复入口拆开 + 进度实时接线 + 列表排版；新单测）
- 时间：2026-10-10
- 触发：翻「下载管理」的渲染代码时发现两件事叠在一起 ——

1. 列表**只在 `task.status == .running` 时画进度条**，可镜像里根本没有 `.running`：
   队列开跑先落库 `running`，紧接着 `synchronizeDownloads()` 读回镜像时被
   `recoveredStatus` 降级成 `waiting` —— 于是「正在下」显示成「排队中」，进度条一次都没出现过；
2. 就算状态对了，进度也不会动：`runner.run(task)` 从来没传过 `onProgress`，
   字节数只有等结果落库时才更新一次。

## 一、状态口径：降级挪到「恢复」，读路径原样

M10b 的恢复策略（`running` → `waiting`）**挪到启动 / 回前台那一次**：
`AppModel.restoreDownloads()` 读库、把 `running` 降回 `waiting` 并**落库**，再由驱动接手。
`RootView` 的 `.task` 与 `scenePhase == .active` 都改走它。

读路径（`GRDBDownloadTaskStore.all()` / `synchronizeDownloads()`）**不再降级** ——
读路径降级会连**正在下**的那条一起降（它也是 `running`），这正是第 1 条的根因。

降级本身仍然必要（不降，那条死任务会一直占着并发位、且永远没人把它推向完成），
所以只是**换了个时机**：从「每次读」挪到「启动 / 回前台」。

## 二、进度：分段数报，不拿前缀冒充总量

`DownloadRunner.onProgress` 的载荷从 `(Int64, Int64)` 换成 ``DownloadProgress``：

| 字段 | 含义 |
| --- | --- |
| `receivedBytes` | 已写进文件的字节数（累计，含续下的基数） |
| `expectedBytes` | 整份总长；**中途恒为 0**（HLS 要等所有片段收完才知道总量） |
| `completedSegments` / `totalSegments` | 片段数进度（直链恒为 0） |

两处刻意的口径：

- **中途不报总量**：M10a 说「宁可显示不确定态，也不要一个错的百分比」——
  「收过的片段长度之和」不是文件总长，拿它当分母会让进度条早早满格。所以 HLS 中途
  的比例只用**片段数**（`completedSegments / totalSegments`），字节比例留给「总量真的知道」的场合
  （直链的 `Content-Length`，等 M25P2 的流式落盘接上）；
- **半途停下的账目也不写 `expectedBytes`**（`PartialStop` 去掉该字段）：同理，
  只见过前缀就不冒充总量 —— 失败 / 暂停的任务 `progress` 是 `nil`（不确定态），
  列表改显示「已下 X」。

接线：`runDownloadQueue` 给每个执行句柄传 `onProgress`，回调蹦回主线程写**镜像**
（`applyLiveProgress`，**只动内存不落库** —— 每收一片写一次库太吵；迟到的回调靠
「只许往前走」防回退）；总片段数放 `downloadRunSegmentTotals` 给界面用，跑完即清。

列表排版（`SettingsDownloadView`）：运行中 = 片段进度条 + 「已下 X · n/m 片」；
没有片段数就退回字节比例 / 不确定态；暂停 = 「已下 X」（账目在暂停时并进任务里）。

## 三、测试

- Store：`running` 读回原样、认不出的字符串仍回落 `waiting`；
- 接线：`restoreDownloads()` 把库里的 `running` 降成 `waiting`（库里也降）且驱动随后能跑完它；
  下载中镜像里状态就是 `running`、`receivedBytes` / `completedSegments` / 总片数都是活的
  （挂在第 2 片上时断言）；
- 执行器：进度回调按片段报数（received 3 → 7、expected 中途恒 0、片段 1/2 → 2/2）。
