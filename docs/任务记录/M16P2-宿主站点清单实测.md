# M16P2 宿主站点清单实测（真 bundle + Windows Node）

## 一、目标

把 `docs/js2p宿主契约.md` 里三处「待实测」变成**可复现的证据**，并据此补齐宿主模式下的站点来源代码：

1. 就绪行 / 实际端口是否与 `NodeReadiness` 解析一致；
2. 站点清单走哪个路由、`sites[].api` 的真实形态；
3. `/spider/*` 动作的真实状态与载荷。

## 二、方法（可复现）

**关键点：不需要 macOS。** js2p 的 spider 服务本身就是 Node 程序，Windows 上同样能跑，
因此「宿主契约」这一类问题可以在任意平台先验证，真机只剩「内嵌 libnode」一件事。

| 步骤 | 命令 / 产物 |
| --- | --- |
| bundle | 复用 `Tools/.cache/index.js`（6,291,879 B，MD5 `35dcc10d533153dbb94298792664ad04`） |
| 运行时 | `python Tools/get_node.py` → 便携 Node **v22.11.0**（sha256 与官方 `SHASUMS256.txt` 一致），只解出 `node.exe` |
| 起服务、抓就绪行 | `python Tools/out/spider_probe.py` → `Tools/out/spider-probe.txt` |
| 用**已加载 key** 复探动作 | `python Tools/out/spider_probe2.py` → `Tools/out/spider-probe2.txt` |
| 静态提取注册路由 | `python Tools/out/bundle_routes.py` → `Tools/out/bundle-routes.txt`（123 条注册） |
| 抓清单全量载荷 | `python Tools/out/spider_probe4.py` → `Tools/out/host-full-config.json`（19,114 B）；结构汇总 `summarize_config.py` |

启动形态：`node index.js`，工作目录 `Tools/.cache/`（`argv[1]` 以 `index.js` 结尾 → 自启动条件满足）。

## 三、实测证据

### 1）就绪行与端口（与代码逐字一致）

```text
{"level":30,…,"msg":"Server listening at http://0.0.0.0:9988"}
CatVodSpiderios listening on http://127.0.0.1:9988
```

→ 与 `NodeReadiness.readyMarker` / `NodeReadiness.port(fromLine:)` **完全一致**；
底层为 **Fastify 5 + pino**（与 M1.5 静态分析结论一致）。

### 2）启动即联网（行为事实，必须写进文档）

```text
[RemoteWexConfig] fetch api url[0]: http://upload.baicanuc.cn/ossfiles/1768320816/api.txt
[RemoteWexConfig] decoded site url: http://103.36.222.35:9595
[RemoteWexConfig] site config loaded, keys=wogg,huajuan,muou,guanying,duoduo,huban,leijing,123pan,shayang,jutou,qiwei,libvio,panku
[RemoteWexConfig] loaded ok, … siteConfigKeyCount=13
```

→ 冷启动**必须能出网**（会拉远端接口并把站点配置文件伪装成 `.jpg`）；离线时上述 spider 不会被加载，
对应路由全部 404。App 需要为此给出可读的失败提示，而不是「站点列表为空」。

### 3）探活与站点清单（原「待实测」项的答案）

| 请求 | 结果 |
| --- | --- |
| `GET /health` | `200 {"ok":true,"name":"CatVodSpiderios"}` |
| `GET /full-config` | `200`，19114 B，顶层 `color / comic / music / pan / read / video`；`video.sites` **85 条** |
| `GET /config` | 与 `/full-config` **同一载荷** |
| `GET /website/api/sites` | `200`，同 85 条，但**不含 `api`**（精简视图） |
| `GET /config/sites/list` | **404** —— 它是 bundle 内部 KV 键（`e.db.get(...)`），不是路由 |
| `POST /spider/<未加载 key>/init` | **404**（例：`csp_AppYsV2`） |

真实站点条目（来自 85 条载荷）：

```json
{"key":"nodejs_douban","name":"豆瓣|首页","type":3,"indexs":1,"enable":true,
 "searchable":1,"quickSearch":1,"filterable":1,"api":"/spider/douban/3"}
```

→ **`api` 是相对路径**（`/spider/<spiderKey>/<type>`，两段）；`type` ∈ {3,4}；`jarSites.count = 0`（无 JAR 站点）。
→ 所以宿主模式下必须先补成 `http://127.0.0.1:<port>/spider/...`，这也是 `Site.isCatSpiderHTTP` 判定能成立的**前提**。

### 4）`/spider/*` 动作

| 请求 | 结果 |
| --- | --- |
| `POST /spider/wogg/init` | `200 {"siteUrl":"https://www.wogg.net"}` |
| `POST /spider/wogg/home` | 路由存在；spider 真实回源被上游 `403`（`ERR_BAD_REQUEST`） |
| `POST /spider/wogg/support` | `404` —— 路由按 spider **实际实现的能力**注册，未实现的动作不存在 |

→ 「宿主 → spider → 上游」整链在 Windows 上已跑通（403 来自上游反爬，不是链路问题）。
→ 现有 `CatSpiderHTTPClient`（POST JSON，`/init|/home|/category|/detail|/search|/play`）
在「相对 `api` 补全后」**完全匹配**实测路由，无需改动路由表。


## 四、交付（代码）

| 文件 | 内容 |
| --- | --- |
| `Packages/CatVodSource/Sources/CatVodSource/Config/HostSiteCatalog.swift` | `HostSiteCatalog`：`GET /full-config` → `HostConfigSnapshot { sites, disabledSiteCount }`；相对 `api` 补全（`absoluteAPI(_:baseURL:)`）；`enable == false` 过滤；`health(baseURL:)` 探活；类型噪声容错（字符串数字 / 字符串布尔） |
| `Packages/CatVodSource/Tests/CatVodSourceTests/HostSiteCatalogTests.swift` | 7 个单测：真实载荷解码（85 条裁剪成 5 条并覆盖噪声）、`absoluteAPI` 四种形态、`spiderKey` 兜底、`health` 四态、非 200/非 JSON 错误映射、缺 `video` 分区 |

设计取舍：

- 只解 `video` 分区，其余分区实测为空 `sites`、`color` 是数组 —— 「全字段必填」的结构会整包解码失败；
- 只覆盖宿主**实际发出**的字段，其余走 `Site` 默认值（**宿主不发的字段不猜**）；
- `HostSiteCatalog` 是纯查询组件（`Sendable` struct + 注入 `HTTPTransport`），与 `CatSpiderHTTPClient` 同风格，便于用假传输层测。

## 五、明确未做

1. **UI 接线**：`HostSiteCatalog` 尚未被 `AppModel` 调用。原因是 iOS 侧还没有 Node 运行时（libnode），
   macOS 侧也还没把「宿主就绪 → 用宿主站点替换远端配置」这条链路串起来；本轮只把**契约层**做实。
2. **iOS 内嵌 libnode**：M1.6 清单第 1–4 项（体积、性能、沙盒能力、端口注入）仍需真机数据。
3. **自动化回归**：~~本轮实测是手动脚本（`Tools/` 不入库），尚未做成 CI 作业。~~
   → **已落地**：`Tools/js2p_contract_probe.py`（入库、可本地跑）+ 独立 workflow `.github/workflows/js2p-contract.yml`
   （`workflow_dispatch` + 每周一 cron，**不挂在 push/PR 上**）。断言分级：就绪行端口与 `GET /health` 是**硬断言**；
   站点数与 `POST /spider/<key>/init` 只作证据（依赖上游远端配置，不该把正常 PR 判红）。
   刻意**不缓存 bundle**：每次验证「当前线上版本」，才能发现上游契约漂移（`publishedMd5` 不一致会记录下来）。
   还有第三种结果：**环境跳过**（DNS/网络/上游不可达 → 退出码 0 + GitHub 警告 + `ENVIRONMENT SKIP` 证据）。
   本作业是手动/定时的非阻断检查，环境抖动变红只会让人开始忽略它，因此与「契约破坏」严格区分。
