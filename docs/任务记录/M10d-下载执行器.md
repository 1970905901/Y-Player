# M10d 下载执行器（真的把文件下下来）

- 状态：`DownloadRunner` 落地，7 条单测（假传输 + 临时目录，全程可跑）；
  **AppModel 接线 / 本地地址接管 / 界面未做**
- 时间：2026-10-09
- 依赖：M10a（任务与队列规则）、M10c（清单展开）、`HTTPTransport`（CatVodNet）

## 一、它只管「照着做」

分层是 M10a 定的：规则在 Core、存储在 M10b、清单展开在 M10c —— 这一层负责执行：
拉地址 → 是 HLS 清单就展开 → 逐片下载**追加写**进同一个文件 → 用 ``DownloadQueue`` 推进状态。

**失败不抛错**：原因写进返回的任务，状态由 ``DownloadQueue/applying(failure:to:)`` 决定
（额度内回排队、用完停失败）。执行层不管重试策略，只回答「这次成没成」——
这样「重试几次、什么时候放弃」这条规则只有一个地方写。

## 二、四处刻意的做法

| 做法 | 为什么 |
| --- | --- |
| 一个任务一个文件，片段按顺序**追加写** | TS / fMP4 片段拼接本身就是可播文件；一次打开文件追加到底 —— 几百片的长剧集上，每片开关一次文件会多出几百次系统调用 |
| **每片都带同一套 header** | 站点鉴权多半挂在 header 上，漏一片就是 403 |
| **失败即停**，不跳过接着下 | 跳过会得到一个「中间少一段」的文件，而且没有任何迹象 |
| 失败时**删掉半成品**，重试从头下 | 续传要对账「下到第几片」，而任务里只存了字节数；这一版不假装支持 |

另外两点：文件名带上**站点 key**（不同站点可能有同名同集的剧，不带会互相覆盖）；
落盘后缀由 M10c 的 `hasInitializationSegment` 决定（`.mp4` / `.ts`）—— 后缀错了，下一环
（本地播放）就会拒开这个文件。

## 三、进度与「总量未知」

`receivedBytes` 每片累加；`expectedBytes` 只有在**每一片**都给了 `Content-Length` 时才敢写
（任何一片没给就留 0 = 未知）。这与 M10a 的口径一致：宁可显示不确定态，也不要一个错的百分比。

## 四、清单（各自独立）

1. **AppModel 接线**：`downloadTaskStore` + 一个「队列驱动」（挑任务 → 跑 → 落库 → 挑下一条）；
2. **本地地址接管**：已下载的集在详情页改成播本地文件；
3. **界面**：详情页下载按钮 + 「下载管理」的任务列表（替换空态卡片）。

## 五、留口

- 加密 / 字节范围清单如实拒绝（见 M10c 与 `refusalReason`）；
- 不做后台下载与限速（M10a 记过）；
- 进度回调只有「累计字节」这一种信号；界面若要「每片一条日志」之类，再加一个事件流。
