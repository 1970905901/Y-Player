## 一、分类重复请求（症状与根因）

症状：首页首屏、切分类、切站点时，**同一个分类同一页会发两次请求**。

根因是「一次加载」被拆成了两条独立触发路径 —— `selectedCategoryID` 既是**用户选择的输入**，
又被 `loadHome()` / `loadCategory()` 当成**程序输出**回写，而 `.onChange(of: selectedCategoryID)` 无法区分这两者：

| # | 路径 | 结果 |
| --- | --- | --- |
| ① | `loadHome()` 末尾 `selectedCategoryID = firstCategoryID` → 触发 `.onChange` → `Task { loadCategory() }`；而 `loadHome()` 自己随后又 `await loadCategory(categoryID:site:)` | 同分类同页 ×2 |
| ② | `loadCategory()` 成功后 `selectedCategoryID = targetCategory` → 同样触发 `.onChange` → 又一次 `loadCategory()` | 同分类同页 ×2 |

## 二、修复：分类加载收敛到**唯一入口**

| 文件 | 改动 |
| --- | --- |
| `HomeView+Data.swift` | 新增 `categoryBinding: Binding<String>`：只把「用户改分类」当事件 —— 值相等直接返回（Picker 初次布局会回写同值）→ 否则重置 `extend` / `page` → `loadCategory()` 一次 |
| `HomeView.swift` | `Picker("分类", selection: categoryBinding)`；**删除 `.onChange(of: selectedCategoryID)`**；在 `selectedCategoryID` 声明处写明约定「程序内回写不发起加载，唯一入口是 `categoryBinding`」 |

为什么这样够：程序内那两处回写不再触发任何加载，而它们各自**本来就**有对应的显式加载
（① 由 `loadHome()` 直接调 `loadCategory(categoryID:site:)`；② 不需要 —— 那次请求刚刚完成）。
不需要新增去重表，也没有"跳过合法请求"的风险。

## 三、延后项：详情页/播放页**不感知接口变更**（明确留给 M9）

现状与风险（**当前版本仍存在**）：

- `VodDetailView` 持有入栈时的 `@State var site: Site?`，`loadDetail()` 走 `model.makeDetailProvider()` ——
  客户端用**当前**配置的 headers，而 `site.api` 属于**旧**接口：接口换掉后是「旧地址 + 新 headers」的串数据；
- `PlaybackView` / `SpiderEpisodePlaybackView` 同样持有入栈时的 `site` / `MediaResource`。

为什么不在本轮修：正确做法是把「接口版本」贯穿整个导航栈（含入栈页的失效判定与重解析策略），
属 **M9 导航重构**范围；只在一层打补丁会出现"提示了但栈里其它页仍是旧的"这种半套状态。

判定规则（M9 落地时按此实现，避免误报）：新接口里**仍有** `site.key` → 静默重载（同接口刷新/冷启动恢复也会 bump 版本号，不能提示）；
**没有** `site.key` → 顶部提示并引导用已有的「换源」；播放中不打断。
