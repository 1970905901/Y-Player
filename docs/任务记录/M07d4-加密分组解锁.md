## 一、先修的是「假开关」

在此之前我们对加密分组的处理是：分组条上画一个 🔒，然后**照常把它下面的频道全列出来** ——
用户看得见锁、却毫无阻拦，等于「看起来做了、其实没拦」。而源把密码写在组名里，本来就是不想让这些组
默认可见。

上游的做法是**根本不显示**这些组：`LiveApi.parse` 之后把 `isHidden()` 的组收进 `mHides`（不进分组列表），
用户输密码（或生物识别）才把匹配的组搬进列表，并且**第一组立刻被选中**。

| 件 | 说明 |

## 三、对齐与差异

| 上游 | 本仓库 | 差异 |
| --- | --- | --- |
| `unlock(pass)`：`pass.equals(item.getPass())` 搬组 + `if (first) onItemClick(item)` | `unlockLiveGroups(with:)` → `LiveGroupAccess.unlocking` | 一致（严格相等、区分大小写；一次能解开同密码的多个组；成功即选中第一组） |
| `onBiometricSuccess()` → `unlock(null)` 解锁**全部**隐藏组 | **不做生物识别** | 空密码不解锁任何组；上游那条路要 `LocalAuthentication`，属于「以后要做」而不是「顺手做」——所以宁可没有，也不做假的 |
| 解锁状态在进程内（`mHides`） | `unlockedLiveGroups` 只在内存 | 一致：重启要重新解锁。密码**不落盘**是有意的（`UserDefaults` 里放源的密码不划算） |
| 触发密码输入的入口（`PassListener` 的调用方）在没取到的那个类里 | 分组条末尾一行「🔒 解锁加密分组（N）」→ push 解锁页 | 我们自己的形态：不用弹层，是因为直播页已经有「节目单」与「直播设置」两个弹层，少一个是一个；写清楚 N 让用户知道还剩几组 |
| `Group.isKeep()` / `skip()` | 不变（`groupRows` 仍只插一个收藏组） | — |

**一个与上游同款的窟窿（记一笔，没修）**：收藏分组的收集**不排除加密组**（`LiveFavorites.group`
与上游 `applyKeepsToGroups` 一样遍历所有组），所以「先解锁收藏过、之后源把该组改成加密」的频道
仍可能从收藏里露出来。我们自己加的那道闸门是「加密分组的频道不给收藏」（上游 `onLongClick` 同样拦），
所以这个口子只在源改分组名/密码之后才可能出现。要修就得连上游一起想，先记着。

> **M07d-5 补的逃生门**：这一轮把加密分组藏起来之后有个副作用 —— 源里组名**本来就有 `_`** 的
> （例如 `央视_高清`）会被拆成「央视 + 高清」而当成加密分组，那串「密码」其实是名字的一部分，
> 于是**永远解锁不了**。直播设置里新增的「组名里的 `_` 不当密码」开关正是给这类源的
> （上游 `Live.pass`），详见 `docs/任务记录/M07d5-组名密码覆盖.md`。

**未做**：生物识别解锁；「记住密码」（上游也没有：解锁是进程内的）。

## 四、验收

- 本机自检：`check_swift.py` + `scan_report.py`（0 条真问题）、行长与注释空格自查。
- CI：待本轮推送（状态行已注明）。
- 人工（需真机 / Mac）：
  1. 用带 `分组名_密码` 的源进直播页 → 分组条里**没有**那一组，末尾有「🔒 解锁加密分组（1）」；
  2. 点它 → 输错密码 → 页面留下「密码不对…」；输对 → 自动退回，那一组出现在分组条里并已被选中；
  3. 组名里的 `_` 后面那段就是密码（区分大小写）—— 大小写错了要失败；
  4. 杀掉进程重开 → 又回到未解锁状态（列表里看不到那一组）；
  5. 换一个源 → 解锁状态清空（上一组的密码不会带到新源）；
  6. 未解锁时「继续观看」/收藏都**不会**把你带进那一组（`selectedLiveGroupObject` 只在可见组里找）。
