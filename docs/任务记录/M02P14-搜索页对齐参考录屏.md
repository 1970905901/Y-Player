## 三、判定与决策（为什么这么做）

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 搜索框怎么放 | 新增基础件 `adaptiveSearchBar`（iOS `.principal` + `.topBarTrailing`；macOS 默认放置 + `.primaryAction`） | 录屏里三者同一行；系统 `.searchable` 做不到。版本/平台差异照 `docs/UI 规范.md` 收敛在 `Platform/` 里 |
| 搜索框外观 | 自绘：圆角浅灰底 + 占位文字，**不加放大镜** | 放大截图确认的样子；这是本页唯一自绘的控件，记在第四节 |
| 历史存哪 | `UserDefaults`（沿用 `AppModel` + `StorageKey` 那套） | 只是 ≤20 条字符串，不值得开表；GRDB 留给收藏 / 进度这类需要查询的数据 |
| 历史序列化 | JSON，不用 `\|` 拼接 | 关键词里可能出现分隔符、换行、表情；拼接式存储会把一条读成两条（单测覆盖） |
| 历史规则放哪 | 纯函数 `SearchHistory`（去重置顶 / 封顶 / 坏存档当空） | 这几条组合在真机上不好造，纯函数才能单测 |
| 重复提交 | `startSearch()` 里 `guard !isLoading` | 连点回车不该并发发两遍同样的请求 |
| 翻页 | 复用 `DiscoverPaging`，触发键 `loadMoreTrigger = 页码-条数` | 与发现页完全同一套判定与触发，不造第二套翻页逻辑 |
| 换站点后 | 只改 `selectedSiteKey`，清空交给 `.onChange` | 沿用 M02P9/M02P10/M02P13 的收口做法，避免同一动作改两处状态 |

## 四、超出 / 未做的部分（诚实记录）

1. **搜索框是自绘的**：SwiftUI 没有「导航栏内嵌搜索框」的原生控件（`.searchable` 的形态不同），
   所以框体按录屏自绘；**放置位仍然用系统原生工具栏槽位**（不是仿制导航栏）。
2. **历史胶囊用自适应列宽网格**：录屏是「宽度撑开就换行」的流式排列，那要 iOS 16 的 `Layout`
   协议自定义布局，而本包最低支持 iOS 15；现在用 `GridItem(.adaptive(minimum: 76))`，
   观感接近，但列宽是均分的（短词会多留白）。
3. **圆形按钮不做结果筛选**：录屏只拍到按钮本身，用户补发的截图确认它是站点面板；
   若要按地区 / 年份筛结果，是另一个里程碑（发现页的筛选胶囊可以复用）。
4. **没有聚合搜索**：仍是「一次搜一个站点」（`AppModel.makeSiteClient()` 的单站点语义）。
