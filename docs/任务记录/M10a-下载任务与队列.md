## 一、为什么先做这一层

设置页「下载管理」一直挂着空态卡片：「离线下载尚未接入：还缺分片下载、任务队列与本地播放地址接管」。
按 M08 / M09 的节奏（先纯逻辑 + 单测，再接传输与界面），这轮先做**任务与队列**。

**上游没有参考实现** —— `Tools/out` 的 `ref-*.java` 里没有任何 Download 相关类。
所以这一块是**本项目自己的设计**，不是照抄协议；「照着上游抄」这条退路在这里不存在，
口径必须写进类型本身，并全部由单测钉住。

## 二、口径（每条都有单测）

`DownloadTask`：

| 规则 | 为什么 |
| --- | --- |
| `id = 站点\|片名\|集名\|线路`，各部分**先转义**再拼 | 去重按它算：换源 / 换线路后 URL 会变，而「这一集的这一条线路」没变。转义是必须的 —— 不转义时 `"a\|b" + "c"` 与 `"a" + "b\|c"` 会撞成同一个键，两集被当成一集 |
| `progress` 是 `Double?`，没有总量时是 `nil` | 用 `0` 会让进度条看起来「卡在开头」，而真实情况是「不知道还剩多少」 |
| 状态机显式收窄（`canTransition`） | `finished` 只能还是 `finished`：否则某条路径会把「已完成」改回「下载中」，文件明明在、却显示在下载 |
| `waiting` 与 `paused` 分开 | 前者「排队等并发位」、后者「用户要求的」—— 用户按过暂停之后不该被自动放回队列 |
| `sanitized` 清落盘名 | 换掉路径分隔符与保留字符、折叠空白、去掉开头的点（`..` 能跳出目录）、空结果回落、按**字符数**截断（按字节会切出半个字） |

`DownloadQueue`：

| 规则 | 为什么 |
| --- | --- |
| 并发上限 2（是规则，不是随手常数） | 手机瓶颈是带宽与发热；同时开五条会把每条都拖慢，还让所有进度条一起卡住 |
| 只自动启动 `waiting` | `paused` 是用户意愿，`failed` 要用户点重试 |
| `expectedBytes == 0` 时不会「收够了」就完成 | 那是传输层的事（流结束才算完），这里不猜 |
| 失败：额度内退回 `waiting` 并计数，用完停在 `failed`（保留原因） | 自动无限重试会把流量与电耗在坏源上，而且用户看不出它在偷偷重试 |
| 手动重试**重置**自动额度 | 手动按一次是明确的意图，不该因为额度用完了就立刻再失败一次 |
| 「整部下载」跳过空地址、按 `id` 去重、时间戳逐个错开 1ms | 空地址建了也只会立刻失败；同一批时间戳全一样时队列顺序不确定（`sorted` 不稳定），下几集的顺序会飘 |

## 三、清单（各自独立，可按需做）

1. ~~**落库**：`CatVodStore` 加一张下载任务表~~ → **已落地**（M10b：协议 + 内存实现 + GRDB + 迁移 `v2.download`）；
2. **传输**：分片下载（HLS 按清单展开）+ 断点续传，调度用 ``DownloadQueue``
   —— 清单展开已落地（M10c），下载与落盘编排未做；
3. **本地地址接管**：已下载的集在详情页改成播本地文件（复用 M6 的 `/proxy` 更省事）；
4. **界面**：详情页的下载按钮 + 「下载管理」的任务列表（替换现在的空态卡片）。

## 四、留口

- **接生产方**（下一步）：`DownloadQueue` / `DownloadRequest` 目前只被单测引用 ——
  孤儿审计会把它们报成「只在测试里出现」，这是**预期的**（消费方是清单里的第 1–4 项），
  不是死代码；与 `DanmakuPlan` 在渲染层落地前的情况同类（M08g 记过这一类）。
- 后台下载（`URLSession` 的 background session）：需要额外的生命周期与调试成本，先做「前台可见的下载」；
- 下载限速（移动网络下有用，先要有真实下载再谈）；
- 空间策略（下载后自动清源缓存之类）—— 等有真实占用数据再定。
