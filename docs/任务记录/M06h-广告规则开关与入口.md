# M06h 广告清理规则的启用开关与界面入口

- 状态：开关落盘、界面入口、规则过滤都已实装并有单测；**内置规则包资产**与**「跳过广告」提示**仍未做（见第四节）
- 时间：2026-10-09
- 依赖：M06d（清理器 / 规则编译 / `/m3u8` 接线）、M06g（分组规则管理 —— 这一页的结构照它做）、
  参考项目 webhtv 的 `bean/HlsRuleState.java`、`api/config/HlsRuleConfig.java`

## 一、这笔账是怎么欠下的

M06d 把清理器、规则编译、`/m3u8` 接线都做完了，但**本地开关那一层只是「写好了」**：

- `HLSAdRuleState`（状态键 + 生效值解析 + 源标识摘要）在 M06d 就落地了，**却没有任何调用点**；
- `refreshAdRules()` 直接 `config.hlsRules.filter(\.isEnabled)` 塞进 `HLSAdRuleStore` ——
  也就是说接口写 `enabled: true` 的规则一律生效、写别的（或不写）一律不生效，用户在本地**什么都改不了**。

「规则能读、但没人能开」是这类功能最容易停在的半成品状态（M06e 的分组规则当时也一样）。
这一轮补上：开关、落盘、界面入口，并且**改完立刻生效**。

## 二、Core：两种「基准」必须分开

| 规则来源 | 生效值 | 上游依据 |
| --- | --- | --- |
| 规则包（`HLSAdRulePackage`） | 本地开关 > 包的 `enabledByDefault` > 关 | `HlsRuleConfig` 的包逻辑 |
| 接口配置（`hlsRules`） | 本地开关 > **规则自己写的 `enabled`** | `compileExternal` |

两者写成两个函数（`resolveEnabled` / `resolveInterfaceEnabled`）而不是一个带参数的分支：
包规则默认关、接口规则默认「看接口怎么写」，判错了表面上是「规则没生效」，
实际是「我们拿错了基准」，混在一个函数里很难查。

`interfaceEntries(_:origin:sourceID:overrides:)` 返回 `Entry(rule, key, isEnabled)` ——
**列表显示的开关**与**真正过滤用的判定**共用同一份键，避免「界面显示开着、实际用的是另一套键」这种
最难察觉的不一致（分组规则那次用的是同一个套路：`GroupRuleConfig.Entry`）。

## 三、界面与存档

- `HLSAdRuleBook`：`{状态键: 开 / 关}`，JSON 落 `UserDefaults`（键 `yplayer.hlsAdRuleOverrides`）。
  状态键由 `HLSAdRuleState.key(origin:sourceID:ruleID:)` 生成 —— **里面已经含源标识摘要**
  （接口地址不落明文），所以这份存档不需要再按接口分桶；
- **传 `nil` = 清掉本地开关**（回到接口的写法），不是「记一个显式的关」。
  少了这条，「恢复默认」会变成「永远关着」，而界面上看起来已经还原了 ——
  和 M06f 里「填成原名 = 恢复原名」是同一类坑；
- `AppModel.hlsAdRuleOverrides` 的 `didSet` 做两件事：落盘 + `refreshAdRules()`。
  于是开关**立刻生效**：`/m3u8` 每个请求从 `HLSAdRuleStore` 现读规则，本机服务不用重启；
- 设置页「播放 → 广告清理规则」：概览（N / M 条生效）、每条一个开关（本地改过的标「已改」、
  左滑「恢复默认」）、作用域摘要（清单 host 后缀 / 正则）；说明节写清没做的部分。
