# M16P6 站点初始化对齐（`POST /init` 生命周期）

- 状态：**已实现并落测**（`CatSpiderInitializer` + `SiteClient` 五个动作 + `AppModel` 共享实例），随 CI 验证
- 触发：核查参考实现 `CatSpider.java` 时发现的**缺一步**，不是真机报错后的补救
- 影响面：js2p（`type=3` + `api` 含 `/spider/`）站点的首页/分类/详情/搜索/播放

## 一、证据（逐字来自参考实现，不是推测）

`Silent1566/webhtv` 的 `app/src/main/java/com/fongmi/android/tv/api/loader/CatSpider.java`：

```java
@Override
public void init(Context context, String extend) {
    post("/init", new JsonObject());
}
```

- 这是 `Spider` 的**生命周期方法**：宿主框架在建 spider 实例时先调 `init`，之后才轮到
  `homeContent` / `categoryContent` / `detailContent` / `searchContent` / `playerContent`；
- bundle 侧按同一契约注册（`docs/js2p宿主契约.md` 第二节）：
  `x.post("/init", t.init?.bind(t) || $zt)` —— **没有实现的 spider 走空实现**，
  所以「不调 init」对那类站点看不出问题；
- 实测（M16P2）：`POST /spider/wogg/init` → `200 {"siteUrl":"https://www.wogg.net"}`，
  即**真有实现的站点确实在这里做准备**。

## 二、我们之前的问题

`CatSpiderHTTPClient.initialize()`（`POST /init`）**只在单测里被调用过**
（`CatSpiderProtocolTests` / `CatSpiderPlaybackTests`），应用流程一次都没发。

后果分两类：对「init 是空实现」的站点无影响（这也是它能一直没被发现的原因）；
对**真有 init 实现**的站点，等于少了准备步骤 —— 症状会是「站点能列出、首页/搜索却拿不到内容」，
而且错误信息只会指向动作本身，很难想到根因在 init。

## 三、实现（按最小改动）

| 文件 | 内容 |
| --- | --- |
| `Packages/CatVodSource/Sources/CatVodSource/Client/CatSpiderInitializer.swift`（新） | `actor`：按 `api` 全路径记忆；保存 `Task<String?, Never>` 让**并发调用等同一次请求**；失败原因留在 `failures` 供诊断 |
| `Client/SiteClient.swift` | 新增 `initializer` 字段（**默认实例**，避免「忘了挂就等于行为退化」）；`home/category/detail/search/play` 的 CatSpider 分支先 `ensureInitialized` |
| `Packages/CatVodUI/Sources/CatVodUI/AppModel.swift` | `private let spiderInitializer = CatSpiderInitializer()`，`makeSiteClient()` 注入同一实例 |

⚠️ **必须由 `AppModel` 持有**：`makeSiteClient()` 每次都会新建一个 `SiteClient`
（界面每处调用各自 new），若让每个 `SiteClient` 自带一份记忆，就等于「每次动作都 init」——
这一条写在 `AppModel` 与 `SiteClient` 的注释里，避免以后被「顺手改成局部变量」。

语义取舍（都对齐参考实现，且各有理由）：

| 取舍 | 决定 | 理由 |
| --- | --- | --- |
| init 失败 | **不阻断**动作，只记原因 | 参考实现的 `post()` 在非 200 时只记日志、返回空串；动作自己会把可读错误抛给界面 |
| init 失败后 | **不重试** | 对应「每个 spider 实例只 init 一次」；否则每个动作前多一次请求（搜索会连发） |
| 记忆键 | `api` **全路径**（含 `/<type>`） | 参考实现按 api 建实例；同一 spider 的不同 `type` 入口各 init 一次 |
| 并发 | 共享同一次请求 | 首页与搜索可能同时触发；不共享会重复 init |

## 四、测试（`CatSpiderInitializerTests`，7 例）

| 用例 | 断言 |
| --- | --- |
| `initOncePerSite` | 两次 home → 路径序列 `["init","home","home"]` |
| `initPayload` | init 的请求体是**空对象**（对齐 `new JsonObject()`） |
| `concurrentCallsShareOneInit` | 并发 home+search → 只 1 次 init，总 3 个请求 |
| `separateSitesInitSeparately` | 两个站点各 1 次；同站点第二次不再 init |
| `initFailureDoesNotBlockAction` | init 404 → 动作仍成功；失败计数 1 且原因含 `/init` |
| `initFailureIsNotRetried` | init 500 → 两个动作只 1 次 init |
| `cmsSiteNeverInitializes` | CMS 站点不发 init、无失败记录 |

同时**显式改掉**了原有的一条期望值：`SiteClientDispatchTests.routesDispatch` 的
`["search","category","detail"]` → `["init","search","category","detail"]`。
这是行为变更被记录下来，不是「把测试改成能过」。

## 五、待观察 / 未做

1. 真机上每个站点首个动作多一次本机回环 `POST /init`，延迟可忽略；若某站点 init 很慢
   （spider 要回源），会把首屏拖慢 —— 到时按站点测量再决定是否改成「进入站点时预热」
   （当前是懒执行，不动就不发）。
2. init 失败原因目前只在内存（`failureNote(forBaseURL:)`），**未接到界面**。
   若真机出现「某站点动作全失败」，可以先看这里；后续可并入「接口管理 → Node 宿主」的诊断输出。

## 七、教训

「只在单测里调用的方法」是一个很强的信号：它说明**生产路径缺了这一环，而测试恰好替它挡住了**。
这次是拿参考实现逐个方法对照才发现的 —— 与 M16P5（`.md5` 输入、缓存文件名）同一类问题：
**先读参考实现，再判定用户/自己的对错**，比照着症状猜要快得多。
