# M03P23 上滑 / 下滑切集（对齐上游 onFlingUp / onFlingDown）

- 状态：**已实现**（本地四闸门全绿 + 新单测；Mac 编译 / 测试 / 上机待 YG）
- 时间：2026-10-10
- 触发：M03P12 / M03P14 两处留口 —— 「上滑 / 下滑切集」当时被放下，理由是 SwiftUI 的 `DragGesture`
  拿不到「甩」的速度，而纵向拖已经被音量 / 亮度占着，按位移猜会在调音量时误切集
  （M03P14 第三节把出路写在「换成 UIKit 的 `UISwipeGestureRecognizer`」）。这一批**没换 UIKit**：
  自己采样算窗口速度（理由见第二节），判据全是纯函数、能单测。
- 依据（上游 mobile flavor）：`app/src/mobile/java/com/fongmi/android/tv/ui/custom/CustomKeyDown.java`
  （`onFling`：多指 / 边缘 / 侧边起手 / 缩放中 / 锁上 / 动画中任一命中就不切；`checkFunc(e1,e2)`：
  `angle > 70°` 且纵向位移 > `DISTANCE = 100` px → 上滑 `onFlingUp`、下滑 `onFlingDown`；
  `isSide(e1)` = 起手在**外侧四分之一**）、
  `app/src/mobile/java/com/fongmi/android/tv/ui/activity/VideoActivity.java`
  （`onFlingUp` → `mVod.nextEpisode(true)`、`onFlingDown` → `prevEpisode(true)`；只有一集时回头 `onRefresh()`）。

## 一、上游口径 → 本项目

| 上游 | 这里 |
| --- | --- |
| `GestureDetector.onFling` 的速度门槛（松手那一刻还在跑才算甩） | 自己采样：`PlaybackSwipeTracker` 只留最近 0.15s 的 `(时刻, 纵向位移)`，松手时算速度（≥ 700 pt/s）；**手指停住再松手 = 0**（窗口里没有位移） |
| `angle > 70°`（几乎笔直上下） | `dy > |dx| × tan 70°`（`verticalSlope = 2.747`） |
| `DISTANCE = 100` px | `minimumDistance = 60` pt（100px 换算过来三十几 dp；取 60 是「够长」与「不误触」的折中） |
| `isSide(e1)`：起手在外侧四分之一就不切 | **照抄**：`isCenterZone(startX:width:)`（起手在中间一半 `w/4 … 3w/4` 才切）—— 侧边四分之一里的纵甩留给音量 / 亮度 |
| 上滑 `onFlingUp` → 下一集；下滑 `onFlingDown` → 上一集 | 同（`PlaybackSwipeAction.next` / `.previous`；`LiveSetting.isInvert()` 只翻转那个 24dp 的动画，我们不做动画，也就不理它） |
| 只有一集 → `onRefresh()`（回头重刷） | 直说「已经是最后一集 / 第一集」，提示 1.2 秒自己收（重刷在这儿说不出意义，不如说清） |
| 甩的同时 `onScroll` 已经调过音量 / 亮度（不撤） | **撤回去**（`revertGestureAdjustment`）：一甩的位移是切集的手势，一次跳掉小半格音量不是用户要的 |
| —— | 没有 `playlist` 的入口（直播 / 下载播放 / 设置页试播）**整个不判甩** —— 那种页面没有「集」这回事，纵甩还是音量 / 亮度 |

## 二、口径与取舍

- **为什么不用 UIKit 的 `UISwipeGestureRecognizer`**（M03P14 当时写的出路）：它得挂在画面层宿主上，
  与 SwiftUI 那几条手势（点按 / 拖动 / 长按 / 捏合）的竞技场关系要一处一处调；而我们要的判据
  （窗口速度 / 角度 / 起手区）本来就能自己算 —— 算出来的东西还能单测（`PlaybackSwipeRulesTests`），
  所以走纯 SwiftUI + 采样；
- **不碰音量 / 亮度的分区**：M03P12 定的「左半屏亮度 / 右半屏音量」原样保留（比上游的外侧四分之一宽）；
  只有「切集」这一件事按上游收进中间一半 —— 不然「快速调音量」会被切集吃掉；
- **同一片区域：慢拖 = 音量 / 亮度、快甩 = 切集**：与 iOS 列表里「拖 vs 甩」的语义一致；
- 采样只在**自绘内核**的手势层（系统内核 `VideoPlayer` 自带手势，不动 —— 本项目惯例）；
- 换集本身走既有的 `switchEpisode(to:)`（M12P1）：资源 / 进度上下文 / 标题 / 弹幕都跟着换，
  不另开一条换集路径。

## 三、故意没做

- `LiveSetting.isInvert()`（上下滑对调 / 动画方向翻转）：上游那个开关只影响 24dp 的动画方向，
  我们不做动画，也就没有可翻转的东西；真要做「上下对调」是另一个用户选项，等有人要再说；
- 甩的画面位移动画（上游 `translationYBy(±24)`）：用那条手势提示条代替（与其它手势一致）；
- 多指 / 边缘起手的额外豁免（上游 `isMultiple` / `isEdge`）：捏合本来就有 `isZooming` 挡着，
  边缘在这儿没有别的含义；
- 系统内核的上滑 / 下滑切集：`VideoPlayer` 自带手势不动。

## 五、教训

- 「SwiftUI 拿不到速度」不是只能换 UIKit：`onChanged` 的每个样本都带时刻，自己在窗口里算就行 ——
  关键是**判据要能单测**（这次是 `PlaybackSwipeTracker` + `PlaybackSwipeRules` 两个纯件）；
- 判「是不是甩」不能拿「起点到终点」算：慢慢拖完再松手，位移一样大。窗口速度就是为这条写的；
- 顺手要看清「同一片区域上叠了几种手势」：音量 / 亮度没动，切集收在中间一半 —— 两种手势语言
  各自有明确的触发条件，才不会互相偷事件。
