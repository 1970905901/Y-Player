- 状态：**已实现**（本地四闸门全绿 + 新单测；Mac 编译 / 测试 / 上机待 YG）
- 时间：2026-10-10
- 触发：M06n 文末「留给后面的」两条 —— 「边下边发（如果需要更早的首字节）」与
  「落盘文件的磁盘配额（现在靠宽限期清扫控制稳态占用）」。
- 依据（上游/参照）：上游没有对应实现（它是「先落盘再发 + 无配额」）——
  这两条是本项目自己补的工程件，口径按 `webhtv docs/integration/proxy-server.md` 的
  「安全要求」第 3 条（请求结束后清理临时文件）与第 5 条（Range / 会话一致性）来定。

## 一、做了什么

### 1）边下边发（`/proxy` 的 2xx GET）

- 老口径（M06b / M06n）：`fetchToFile` **整份下完**才把文件交给 FlyingFox 发 ——
  大文件（尤其播放器不带 Range 直接要整份的那种）要等全下完才出首个字节；
- 新口径：走传输层的 ``HTTPStreamingTransport``（M25P2 为直链下载做的那条，`URLSession.bytes`
  攒 64KB 块）—— **响应头一到就回**，响应体由 ``LocalProxyFileBuffer`` 边收边写临时文件，
  FlyingFox 的响应体（``LocalProxyFileSequence``）在另一头读**同一份文件**：写到哪发到哪；
- 长度口径：上游 `Content-Length` 有 → 响应体带 `Content-Length` 发；
  没有 → 交掉 chunked（FlyingFox 见 `count == nil` 自动加 `Transfer-Encoding: chunked`）；
- **非 2xx 仍走内存那条**：错误码与错误页原样回（受 ``LocalProxyUpstreamClient/maximumBodyBytes``
  约束），不该被算成「媒体文件」；
- 传输层不支持流式（测试替身 / 别的实现）时退回 M06b 的落盘转发，行为不变。

### 2）磁盘配额 + 「在用登记」

- **在用登记**（新）：正在写 / 正在发的文件登记在册（``LocalProxyTempFiles/markInUse(_:)``），
  清扫**永不动**它们 —— 没有这条，「边下边发」的文件会在传输途中被扫掉；
- **发完即删**（新）：``LocalProxyFileBuffer`` 释放（响应体发完 / 客户端断开 / 响应被丢弃）时
  注销登记并删文件 —— 这是 M06n 缺的那块拼图（当时 FlyingFox 的响应体没有「发完了」的回调，
  只能靠 15 分钟宽限期兜底）；
- **配额**（新）：`LocalProxyTempFiles.maximumBytes`（默认 1 GiB）—— 清扫时总量超线就按
  **最旧先清**淘汰**不在用**的文件；
- **纯策略**：清扫的两条规则（宽限期 / 配额）抽成
  ``LocalProxyTempFiles/plan(entries:now:maximumAge:quota:)``（纯函数，随机 / 配额都能单测），
  `sweep()` 只负责列目录、执行与记账。

## 二、口径与取舍

- **文件就是缓冲**：块不堆内存（磁盘比内存便宜、也不怕大），代价是「客户端慢读」时占用写在盘上 ——
  由配额与「发完即删」兜住；
- **在用的文件宁可超配额也不删**：单个大文件自己就超过配额（4K 电影几个 GB）也照发 ——
  删掉 = 当场断流，比超配额严重得多；
- **上游提前收尾 = 断连接**：写不够 `Content-Length` 时读侧抛 ``LocalProxyFileBuffer/BufferError``，
  FlyingFox 的发送循环随之抛错、连接关掉 —— 不把短的实体留在 keep-alive 流里
  （那会让下一条响应被错位解析）；客户端看到的是「断了」，会带 Range 重试；
- **不发「预计长度」时不上限**：上游不给 `Content-Length` 且客户端一直读，文件会一直长；
  真兜底是客户端断开（缓冲释放 → 撤下载 → 删文件）与每次请求的清扫 ——
  不给「媒体文件」设字节上限（那会直接把大片拦死）；
- 清占用靠 **deinit 删除** 而不是「定期扫」：文件的生死跟着「谁还需要它」走，宽限期只治
  「没登记就躺在那儿」的残渣（崩溃、上一进程遗留）。

## 三、故意没做

- **按盘剩余空间 / 按可用空间比例定配额**：先固定 1 GiB 一档（要调就改 ``maximumBytes``）；
- **落盘文件的复用 / 文件池**（同一个 Range 再请求一次仍会重新落一份）：
  收益（省一次下载）与代价（要判「这份文件还算不算新鲜」）不成比例，不做；
- **Range 切片转发 / 断点续传**：上游的 Range 响应体原样搬（M06n 的口径不变）；
- 非 2xx 的上游错误体落盘：错误页都很小，内存那条够用。

## 五、教训

- **「没有回调」是可以自己造的**：M06n 当时判定「FlyingFox 的响应体没有发完回调 ⇒ 只能宽限期清扫」——
  自己写响应体（`AsyncBufferedSequence` + `HTTPBodySequence`）之后，「发完了」就是**对象释放**这一刻，
  宽限期从「主办法」降级成「兜底」；
- **清扫动的是共享目录**：集成测试里没法安全地造「超配额」场面（并行用例也有文件在目录里）——
  把策略抽成纯函数再单测，集成测试只钉「老了会清、在用的不碰」。
