# M06e 站点分组条（`groupRules` 形状修正 + 分组抽取与顺序）

- 状态：**抽取 / 生效集合 / 顺序 / 面板接线都已实装并有单测**；规则管理界面（自建规则、AI 规则、内置规则开关）与站点自定义名是下一步（见第六节）
- 时间：2026-10-08
- 依赖：参考项目 webhtv 的 `bean/GroupRule.java`、`setting/GroupRuleConfig.java`、`setting/SiteGroupOrderStore.java`、
  `setting/SiteNameRules.java` + 它自己的 `GroupRuleTest` / `SiteGroupOrderStoreTest`

## 一、`groupRules` 是**站点名**的分组规则，不是「直播分组」

`协议兼容矩阵` 里这一格原先写着「`groupRules`（直播分组，M7）仍未接」—— 这句话本身就是那个 bug 的化石：

- 上游的链路是 `SiteDialog → Site.getGroups → SiteNameStore → SiteNameRules.groups → GroupRuleConfig.extract`，
  **吃的是站点名**（`💥木偶|4K` → `4K`），输出是站点面板顶上那条分组条的标签；
- 而本项目的模型是 `{name, hosts, regex: [String]}` —— `hosts` 这个字段在上游**并不存在**，
  是「给直播主机分组」这个错误理解留下来的；
- 后果与 M06d 的 `hlsRules` 完全一样：**静默失效**。字段名 `name` / `regex` 能对上，
  但 `regex` 是字符串、配置给的是字符串，模型却要求数组 ⇒ 一条规则都解析不出来，不报错、也没人发现。

上游的 `GroupRule` 是：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | 字符串 | 规则 id（内置规则是固定串，用来存「关掉哪条」） |
| `name` | 字符串 | 规则名（只在管理界面显示） |
| `regex` | **字符串** | 一条正则；抽**第 1 个捕获组** |
| `enabled` | 布尔 | 接口规则自己写的开关（内置规则恒为真，只看有没有被本地关掉） |
| `source` | 字符串 | `builtin` / `user` / `interface` / `ai` |
| `wrapBracket` | 布尔 | 抽出来的标签要不要套成 `[标签]` |

所以这一轮：模型对齐形状、抽出纯逻辑、再把面板接上（纯逻辑先行，理由同 M06d —— 不然又是「能读、没人用」）。

## 二、抽取语义（逐条对齐 `GroupRuleTest`）

四条内置规则（正则照抄上游，`GroupRuleConfig.builtins`）：

| 规则 | 正则 | 命中例 |
| --- | --- | --- |
| 方括号标签 | `\[([^\]]+)\]` | `[主力][短剧]我的站` → `主力`、`短剧` |
| 竖线后缀 | `(?i)(?:[|｜])\s*([^|｜]+?)\s*$` | `💥木偶|4K` → `4K`；`某某｜1080P` → `1080P` |
| 框线分隔 | `(?i)┆\s*([^┆]+)\s*$` | `🪵┆木偶┆4K` → `4K` |
| 圆点后缀 | `(?i)(?:[•·])\s*([^•·]+?)\s*$` | `热播·APP` → `APP` |

- 抽 **第 1 个捕获组**，没参与匹配就退回整段匹配（上游 `matcher.group(1) != null` 的判法）；
- 结果去首尾空白、去重、保持出现顺序；`wrapBracket` 时套 `[标签]`（已经是方括号的不重复套）；
- **坏正则判为不可用**（`isValid == false`），`extract` 返回空 —— 不抛、不崩，也不变成「命中一切」；
- **AI 来源的规则要过安全子集**（逐条对齐 `isSafeAiRegex`）：只放行字面量 / 字符类 / `\s\S\d\D\w\W` /
  非捕获组 `(?:…)` / 少量量词，且必须**正好一个捕获组**；`.`、`|`、`{n,m}`、回溯引用、嵌套重复一律拒。
  理由：AI 写的正则没人 review，`^(a|aa)+$` 这种在长文本上会指数回溯 —— 卡在匹配入口比事后加超时省事。
  超长文本（>256 字）直接不跑。用户规则不受这条限制（上游也只卡 AI）。

**一处刻意偏离**：缺 `id` 时上游随机生成 UUID，本项目按 `name|regex` 算稳定 id。
上游那样每次加载都是新的 id，而「关掉某条规则」是按 id 存的 ⇒ 一重启开关就失配。这里改成稳定的。

## 三、生效集合与顺序（对齐 `GroupRuleConfig` + `SiteGroupOrderStore`）

- 生效规则 = 内置规则 + 接口规则，各自减掉「被本地关掉的 id」，再滤掉编不出正则的；
- `extract` = 所有生效规则的结果**合并去重**、保持顺序；
- 顺序三件套（`CatVodCore.SiteGroupOrder`）：
  - `order`：存过的按存的次序排前面，**没存过的按默认顺序接在后面**（默认顺序 = 按站点顺序首次出现）；
  - `mergedVisibleOrder`：拖动后与「完整顺序」合并，**保留隐藏分组的槽位** ——
    分组条只显示有站点的分组，但顺序要按全集存，否则一个分组因为当下不可见被挤到末尾，下次出现位置就乱了；
  - `move`：一次一格，越界 / 找不到 / 方向非法都返回 false 且不动数组。

## 四、界面接线（站点面板）

- 站点抽标签在 `DiscoverSiteList.tags(sites:rules:)`，吃的是**显示名**（`title(for:)`：没名字回落 `key`）——
  与上游 `SiteNameRules` 吃「生效名」是同一口径（我们还没有站点自定义名，所以两者一样，口径先钉在这）；
- 面板（`DiscoverSitePanel`）顶上加一条横向分组条：**有分组才显示**（对齐上游「空就隐藏」），
  点一个分组只留这个分组的站点，**再点一次取消**（上游同款交互，没有额外的「全部」项）；
- 抽标签要跑正则，所以标签在 `.task` 里算一次缓存起来；分组顺序与筛选都是基于它的廉价计算 ——
  「上移/下移之后立刻看到新顺序」不需要重新抽标签；
- 顺序存档 `SiteGroupOrderBook`：**接口地址 → 分组名数组**（JSON 落 `UserDefaults`，键 `yplayer.siteGroupOrder`），
  坏存档当空、空桶丢掉（存档坏了最坏就是回默认顺序，不该让面板打不开）；
  按接口分桶的理由同直播那几本书 —— 换接口时分组名整套换掉，混在一起会互相污染。
  落盘走 `AppModel.siteGroupOrders` 的 `didSet`（与 `liveFavorites` 一个写法）。

**与上游的差异**：上游的分组条是**长按拖动排序**，本项目改成**长按弹出「上移 / 下移」菜单** ——
iOS 上横向滚动的手势和拖动排序会打架，菜单同样的结果、少一个手势。顺序规则本身（含隐藏槽位）与上游一致。
