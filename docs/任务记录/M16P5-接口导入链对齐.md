- 状态：**已实现并落测**（`ConfigLocator` / `SourceRepository` JS 分支 / `SourceCacheStore` / Node 运行时的 `NODE_PATH`）
- 触发：真机截图显示接口加载失败（`配置不可用：配置不是合法 JSON：dataCorrupted(… column 2)`）

## 一、参考实现怎么做的（逐字证据）

来源：`Silent1566/webhtv`（Android/Java，FongMi/TV 血统）

### 1. 接口地址形态 —— `NodeBundle.java` 类注释

> 猫源 bundle（CatPawOpen 的 `index.js`）的下载、校验与本地缓存。
> **用户填的是 `.../index.js.md5` —— 那个地址返回 32 位校验值，真正的 bundle 在去掉 `.md5` 后缀的地址上。**
> 每次启动只拉几十字节的 md5 比对，命中就用本地缓存，避免重复下载 1.2MB 的 bundle。

对应的两个纯函数：

| 函数 | 规则 |
| --- | --- |
| `digestUrl(url)` | `url` 已以 `.md5` 结尾就是它，否则 `url + ".md5"` |
| `bundleUrl(url)` | 去掉 `.md5` 后缀 → 真正的 bundle 地址 |

### 2. 缓存判定与三条硬政策 —— `ensureRemote` / `remoteMd5` / `remoteSourceKey`

| 项 | 参考做法 | 我们的实现 |
| --- | --- | --- |
| 元数据 | 只拉几十字节的 `.md5`；超时 **3 秒**（注释：「复用判定要抢在用户感知之前给结论，慢比错更难接受」） | 同（`fetchDigest`，3 秒） |
| 摘要校验 | `isMd5`：**32 位十六进制**才算校验值，否则按「没有校验值」 | 同（`MD5.isDigest`） |
| 未校验内容 | **绝不下载未校验的 bundle**：拿不到校验值只允许用已校验过的缓存 | 同（拿不到校验值 + 无缓存 → 直接报错，不下载） |
| 身份 | `remote:<bundleUrl>:<bundleMd5>:<configMd5>` —— URL 相同但 md5 变了要重下（否则会继续跑旧 JS） | 摘要比对（命中即跳过下载） |
| 落盘 | 运行目录固定 `…/node/bundle/index.js`（+ `index.js.md5`、`index.config.js`、`data/`、`port`、`boot.js`），目录私有且可写 | 每接口一个 `bundle-<md5(url)>/index.js`（+ `index.js.md5`） |

### 3. 运行环境 —— `NodeBoot.java`

参考实现**不靠 bundle 自启动**，而是生成 `boot.js` 注入：

| 注入项 | 作用 | 我们是否采用 |
| --- | --- | --- |
| `globalThis.catServerFactory` | 关掉自启动，改由宿主 `require` 后调 `start(config)` | ✗ 不采用：我们实测的 bundle 自启动可靠（就绪行可解析），链路已通过模拟器验证 |
| `globalThis.catDartServerPort()` | bundle 把 `/msg` 回调 POST 回宿主 | ⏳ 未用（契约里的可选能力） |
| `process.env.DEV_HTTP_PORT` | Java 侧先探空闲端口再指定（该 bundle 默认随机端口且无 `EADDRINUSE` 重试） | ~ 我们注入首选端口，bundle 自己 `+1` 重试，就绪行给实际端口 |
| `process.env.NODE_PATH = <bundle>/data` | **必须**：bundle 的 `db.json` 与代理 `vod_cache` 落在这里；不设会回退到进程 CWD，代理「返回 200 但 0 字节」 | ✅ 已采用 |
| `uncaughtException` / `unhandledRejection` | 记录而不是让进程无声死掉 | ✅ 已采用（`NodePreloadScript`，另附 `process.exit` 拦截与落盘日志） |
| `setInterval(…, 60000)` | listen 失败时事件循环会空掉、`node::Start` 直接返回，进程「死得无声无息」 | ✗ 未用（我们用就绪超时 + 落盘日志暴露） |
| 端口落盘 `port` 文件（tmp + rename 原子写） | 由宿主轮询读取；因为魔改 bundle 可能起多个 HTTP 服务，**句柄顺序不保证**，需逐个探 `/config` | ⏳ 备选：我们靠 stdout 就绪行（已实测可靠） |

## 二、由此修正的我们这边的问题

1. **分类错误**（真机现象的直接原因）：`.js.md5` 被当成 JSON 配置 →
   现在 `ConfigLocator` 静默归一化为 `.js`，**且不产生「已纠正」告警**（它是正规写法）。
2. **落盘文件名错误**（更严重，且第一轮 CI 没覆盖到）：bundle 曾缓存为 `config-<md5>.js`，
   而 bundle 的自启动条件是 `argv[1]` 以 `index.js` 结尾 → 改名成
   `bundle-<md5(url)>/index.js`（每接口一个目录，与参考一致）。
3. **`NODE_PATH` 缺失**：bundle 的 db/代理缓存没有可靠根目录 → 启动前创建同级 `data/` 并注入。
4. **失败信息不可读**：不再把 `DecodingError` 原文甩给界面，改为可操作说明
   （32 位摘要文本 → 指明可填 `index.js` 或 `index.js.md5`；像 JS 脚本 → 提醒确认 `.js` 结尾）。

## 三、对我们的后续影响（待办）

- `index.config.js`：参考的 bundle 有第二个成员（配置），站点从 `server.config.<key>` 取参数，
  「空对象会让它们抛 undefined」。我们实测的 bundle 用 `/full-config`，暂不需要；
  若将来接入该形态的 bundle，需要在 `NodeBundle` 等价物里支持第二个成员。
- 「端口落盘 + 逐个探 `/config`」是比 stdout 更稳的端口发现方式（能穿过「魔改 bundle 起了多个服务」），
  当前 stdout 就绪行已验证可用，保留现状并在此记录备选。
