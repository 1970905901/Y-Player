## 三、真实生效的路径（逐条可追）

1. **源缓存时间**：`AppModel.load(forceRefresh:)` → `loadSource(target:forceRefresh:repository:)` 先问
   `repository.loadCached(configURL:maxAge:)`；命中就用缓存（不联网），过期或「刷新接口」才走网络。
2. **首页缓存时间**：`HomeView+Data.loadHomeResult(site:force:)` 与 `loadCategory(...)` 先查
   `model.cachedHomeResult(key)`，命中直接渲染、不发请求；`force: true`（工具栏刷新）绕过。
3. **三个清空**：源缓存 → `clearSourceCache()`；首页缓存 → `clearHomeCache()`；全部 → `clearAllCaches()`。
   「全部缓存」大小 = 两处之和（下载占用与本地库不算缓存，页内写明）。
4. **下载管理**：`StorageSpace.snapshot(downloadDirectory: AppModel.downloadDirectory)`；离线下载未接入，
   所以「下载 0B / 暂无下载内容」是真实状态，卡片下方写明缺什么。
5. **弹幕 API**：4 个地址真实保存（`DanmakuAPIConfig` 往返已单测）；执行链属于 M8，页内如实标注。
6. **显示视图**：`VodDetailView.content` 按 `model.playbackPageLayout` 在 `compactLayout` / `embyLayout` 之间切换，
   两者共用同一份数据与同一套工具（收藏 / 换源 / 续播）。
7. **自动播放**：`.task` 里 `loadDetail → loadProgress → loadFavorite → scheduleAutoPlayIfNeeded()`；
   有观看记录时不触发（留给「上次看到」），一次进入只触发一次。
8. **日志开关**：`AppModel.isEngineLogEnabled` → `applyLogPreferenceToHost()` /
   `refreshHost` 里的 `service.setLogPersistence(_:)` → `NodeRuntimeLaunching.setPersistsHostOutput(_:)`
   → `NodeMobileRuntime.persistIfNeeded(_:)` 追加落盘。
9. **导出**：`fileExporter` + `EngineLogDocument`；导出优先落盘日志，没有落盘时退回内存里的最近输出。

## 八、本轮 CI 红的原因与修复（exit 70）

- 症状：`Lint (SwiftLint / SwiftFormat)` 以 **exit code 70** 失败 —— 这是 SwiftFormat 的
  「内部 / 解析错误」，与「格式违规（=1）」不是一回事；`SwiftPM tests` 因 `needs` 关系被卡住。
  而上一提交（图标换新）在同一条流水线上是全绿（8m12s），所以问题出自本批改动。
- 原因：`NodeMobileRuntime.swift` 在 `consume(_:)` 之后插入 `persistIfNeeded` / `setPersistsHostOutput`
  时**多留了一个 `}`**，actor 在 `markReady` 之前就被关闭，其后所有成员函数落在类型外面：
  文件语法不成立 ⇒ SwiftFormat 解析失败退出 70（Swift 编译同样会挂）。
- 定位方式：本机没有 Swift 工具链、GitHub 匿名 API 又撞上限流，于是写了
  `Tools/out/syntax_scan.py`（花括号 / 字符串 / `#if` 分支配对扫描）—— 一次就扫出
  「NodeMobileRuntime 第 326 行花括号提前闭合（depth=-1）」。
- 修复：删掉那个多余的 `}`；复扫本批全部 20 个新增 / 修改文件，全部 OK。

### 8.2 第二个红灯：格式违规（exit 1）

- 症状：删掉多余花括号后，Lint 的退出码从 70 变成 **1**（「有文件需要格式化」），16s 就失败。
- 困难：SwiftFormat 只把「哪个文件要改」写进 job 日志，而 **job 日志需要登录才能看**；
  本机终端不稳、匿名 GitHub API 又撞上限流（务必记住这条：跑脚本查 CI 要趁早）。
- 办法：临时加 `.github/workflows/format-report.yml` + `Scripts/format_report.py` ——
  在 CI 里跑 `swiftformat --lint`，失败就真跑一次 `swiftformat`，再用 `git diff` 把每一处改动
  通过 `::error file=…::` / `::notice::` 变成 **annotations**（annotations 不需要登录就能读）。
- 结果：注解显示全仓库**只有一处**需要改 —— `SourceRepository+FreshCache.swift` 第 34 行的
  `try decodeConfig(try Data(contentsOf: cacheURL))`（内层 `try` 会被外层吸收）。
- 修复：改成 `try decodeConfig(Data(contentsOf: cacheURL))`；两个临时文件在 CI 转绿后删除。

### 8.3 一条操作教训：每个 run 会取消上一个 run

`build.yml` 有 `concurrency: cancel-in-progress: true`，所以**连续修复推送时，前一个 run 会被取消**
（`core-tests` 那 4–8 分钟常因此没跑完）。这次 5 个提交里有 3 个的 `SwiftPM tests` 都是被取消的，
等于编译一直没被真正验证过 —— 想拿编译结论，就得**推完停手等它跑完**，不要接着推下一个修复。

> 教训：终端不可用 + 无法编译时，「先把产物落盘、再用脚本做一遍结构自检」比反复猜要快得多 ——
> 这类「少一个 / 多一个花括号」的错，配平脚本能立刻抓到，而肉眼看几百行很难发现。


本机 PowerShell 会话崩溃（PSReadLine `SetCursorPosition` 异常），长命令会被逐字符打散、
输出捕不到，因此**这一批改动还没有跑过一次编译**。已用「脚本落盘 + 极短命令 + 读产物」的方式
完成全部读写，但编译验证需要在终端恢复后进行。
