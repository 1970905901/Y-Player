# M10m 暂停正在下的那一条（取消执行句柄）

- 状态：**已实现**（`DownloadRunner` 认取消 + `AppModel` 逐条执行句柄；执行器 3 条新单测 + 接线 2 条）
- 时间：2026-10-10
- 依赖：M10d（执行器）、M10e / M10h（接线与前台驱动）

## 一、为什么：按了暂停等于没按

M10e 的留口写着「暂停正在下的那一条要等当前分片结束」。实际比这还糟：

1. 暂停只把状态改成 `paused`，执行器完全不知道 —— 它接着把整条下完；
2. 下完（或失败）后把结果落库，**把 `paused` 盖掉**：成功盖成「已完成」，失败盖成「排队中 / 失败」并计数；
3. 失败那条还会被驱动当待办**自动重试** —— 用户的暂停被彻底忘掉。

## 二、怎么做

| 决定 | 为什么 |
| --- | --- |
| 一条任务一个 `Task` 句柄（`AppModel.downloadRunTasks`），不再用 TaskGroup 直接跑 | `TaskGroup` 只能**整组**取消，取消不了单独一条 |
| 暂停 = 先落「已暂停」，再 `cancel()` 句柄 | 界面当场变；取消是给执行器的信号，不是状态本身 |
| 删除 / 清空也取消在跑的那条 | 任务都删了还接着跑完，是白占带宽 |
| 执行器用 `Task.isCancelled` 判定，不看错误类型 | `URLSessionTransport` 会把底层 `CancellationError` 包成 `CatVodError.network` —— 到执行器手里错误类型已经不可信 |
| 取消 → `DownloadQueue.pausing`（回 `.paused`），不当失败 | 暂停不该吃重试额度，也不该被自动重试拉起 |
| 停止点：分片之间 `Task.checkCancellation()` + 当前请求被取消 | 合作式传输（URLSession）当场中断；不合作的传输至少在分片边界停 |
| 句柄在**任何 await 之前**建好、登记 | 挑选到登记之间没有挂起点，暂停要么在挑选时就被跳过、要么一定取消得到句柄（不会出现「暂停没人可取消」的窗口） |
| 「旧结果不盖新决定」 | 非「已完成」的结果只落给仍在跑（或同样暂停）的任务 —— 典型是「暂停后马上点继续」：晚到的取消结果若把任务按回暂停，队列会卡死 |

半成品与账目留着（M10n 起）：暂停后点「继续」从账目那一片接着下。

## 三、测试

- 执行器（`DownloadRunnerTests`）：取分片途中取消（合作式）→ 回「已暂停」、不吃重试额度、半成品删掉；
  开跑前已取消 → 一个请求都不发；不合作的传输 → 在分片边界停（下一片不发）、半成品删掉；
- 接线（`DownloadWiringTests`）：暂停正在下的那条 → 驱动收尾后仍是「已暂停」，不是失败也不是完成；
  暂停后马上点继续 → 接力跑完，晚到的取消结果没把它按回去。

## 四、上机首验踩的两个坑（连着两红）

### 一号坑：镜像里的 `running` 是假的（`d1596f2` 修复）
 第一版在批处理里用「镜像里这条是不是还是 `running`」来挡
「批量落库与开跑之间被暂停」，可 M10b 的恢复策略是**库里读出来的 `running` 一律降级成 `waiting`**
（`GRDBDownloadTaskStore.recoveredStatus`）—— 这个条件在 GRDB 下永远不成立，任务被 `continue`
跳掉后 `while true` 立刻重挑同一条，变成死循环烧 CPU（Mac 首验：`sample` 显示主线程卡在
`runDownloadQueue` 的 `save` 上，测试进程跑了 17 分钟、吃了 14 分半 CPU）。

修法两条（都写进代码注释了）：

1. 不再看镜像状态；句柄在批处理的**第一个 await 之前**建好并登记 —— 单 actor 上，
   挑选到登记之间没有挂起点，用户按的暂停不可能插进来；
2. `applyDownloadOutcome` 的「旧结果不盖新决定」改按**结果的状态**分派：
   `.waiting / failed` 不盖暂停（防把暂停拉回自动重试）、`.finished` 永远落库。
   **别再引入「当前是不是 `running`」这类开关** —— 它在 GRDB 下恒假，
   跳过结果 = 状态永不变 = `while true` 空转。

### 二号坑：两次 `save` 的落地顺序没保证（`60e0ea8` 修复）

修掉一号坑后，「暂停后马上点继续」还是红：状态回到「已暂停」、第二趟没跑。
根因是**抢写**：`downloadStore.save` 是**离 actor 的 await**（非隔离 async 跑在全局执行器上），
「读镜像 → 改 → 落库」不是原子的 ——

- 暂停写好 `paused`、取消句柄；用户紧接着点「继续」写下 `.waiting`；
- 执行器被取消的 `.paused` 结果晚一步到，apply 读到的镜像还是 `.paused`（继续的回写还没轮到），
  于是又落一次 `.paused`；这次 save 提交晚、落地更晚，把刚写下的 `.waiting` 盖回去；
- 任务停在暂停、没人再启动它。

修法：**取消结果（`.paused`）不落库** —— 暂停状态由 ``pauseDownload`` 先写（先写状态再取消句柄），
执行器这趟不带新信息；不写，就没得抢。失败结果仍要落（带重试计数），用户按着暂停时跳过。

教训一句话：**同一个状态不要有两条路径各写一遍**；用户操作写下的状态，执行器的回执只该「别盖」。
