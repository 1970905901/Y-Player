## 一、上游三层，我们做两层

上游的候选规则是三处拼起来的，`GroupRuleConfig.entries()` 的顺序就是它们出现的顺序：

| 位置 | 来源 | 谁管开关 |
| --- | --- | --- |
| 1 | 内置四条（`builtins()`） | **只看**「本地关掉的 id」，不看它自己的 `enabled` |
| 2 | 接口配置（`groupRules`） | 自己的 `enabled` × 没被本地关掉 |
| 3 | AI 生成（`AiGroupRuleStore`） | 自己的 `enabled` |
| 4 | 用户自建（`GroupRuleStore.loadUser()`） | 自己的 `enabled` × 没被本地关掉 |

本项目做 1、2、4；**第 3 档在 Core 里留了位置**（`entries()` 的注释写明插在哪），
设置页也直说未做 —— 那一档要连 AI 服务，属于后续里程碑。

顺序不是随便定的：同一段站点名被多条规则命中时，标签的先后就按这个顺序排。
所以 `entries()` 里那条注释不是客套话，改顺序前先想清楚标签会怎么变。

## 二、Core 语义

- `GroupRuleConfig.Entry(rule, isEnabled)`：把「这条规则现在算不算生效」单独算一次。
  内置与其它来源的判法**不同**（见上表），塞进一个布尔表达式里迟早写错 —— 上游把它拆成 `Entry` 是有原因的；
- `activeRules()` = `entries()` 里 `isEnabled && rule.isValid` 的那些；
- `enabledCount()` / `totalCount()`：设置页那行「已启用 N / 共 M」；
- 没有 id 的规则直接跳过（对齐上游 `TextUtils.isEmpty(rule.getId())`）。

## 三、界面

- **存档**：`SiteGroupRuleBook` = `接口摘要 → {关掉的规则 id, 自建规则}`，JSON 落 `UserDefaults`
  （键 `yplayer.siteGroupRules`）。上游把「关掉哪些」和「自建哪些」分两份存，这里合成一份 ——
  它们本来就是「接口配置 + 我的本地调整」的两半，放一起读起来更直白；桶键同样是地址摘要（理由同 M06f）；
- **AppModel**：`toggleSiteGroupRule(_:)` / `addSiteUserRule(name:regex:wrapBracket:)` /
  `removeSiteUserRule(_:)`。两条刻意的规则：
  - 加规则时**编不出来就不存**（否则用户会以为设置坏了）；
  - 删规则时顺手把它从「关掉的 id」里摘掉，不留垃圾；
- **面板输入打包**：`DiscoverSiteRuleInput`（接口规则 + 自建规则 + 关掉的 id + 自定义名）是一个 `Hashable` 值，
  面板用 `.task(id: ruleInput)` 一处盯住所有会影响标签的输入 —— 改名、开关规则、加删自建规则，任一变化都重抽；
- **设置页**：设置 → 站点分组 → 分组规则。三节（内置 / 接口 / 自建）+ 概览 + 新增 + 说明：
  - 每行显示名字、正则（等宽小字）、开关；正则编不出来的标黄警告；
  - 自建规则可以左滑删除；接口规则只能开关（改了也会被下次加载覆盖，页脚写明）；
  - 新增弹窗给两个能直接照抄的例子（方括号、竖线）。

## 四、测试

- `GroupRuleConfigTests`（9 条）：候选顺序（内置 → 接口 → 用户）、用户规则参与抽标签与按 id 关闭、
  内置忽略自身 `enabled`、条数统计（编不出正则的算候选不算生效）、无 id 跳过；
- `SiteGroupRuleBookTests`：往返（含自建规则的 `wrapBracket` 与抽标签能力）、脏存档降级、解码清洗、
  写入 / 清空删桶 / 没有桶名时不动存档；
- `DiscoverSiteGroupTests` 增补：自建规则抽出的标签进分组条、关掉规则后标签立刻消失、
  关掉内置竖线规则后 `某站|4K` 不再是 4K 分组。
