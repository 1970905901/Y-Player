# M10b 下载任务落库（协议 + GRDB + 迁移 v2）

- 状态：`DownloadTaskStore` 协议、内存实现、GRDB 实现与迁移 `v2.download` 落地，11 条单测；
  **AppModel 接线与传输层未接**（等有生产方再接，避免摆一个没人写的库）
- 时间：2026-10-09
- 依赖：M10a（任务与队列的纯逻辑）；存储层沿用 M08b 的 GRDB 与失败留痕约定

## 一、迁移只能追加

`GRDBDatabase` 的迁移是 `DatabaseMigrator`，v1 里建了收藏 / 进度 / 搜索历史 / 站点四张表。
这轮加下载表时**追加成 `v2.download`**，没有去改 v1 —— 已经装过的库跑过 v1 了，
改它的内容不会重跑，结果是「新装的库有这张表、老库没有」这种最难查的差异。

## 二、三个与播放进度不同、值得写下来的决定

1. **`status` 存原始字符串**（`waiting` / `running` …），不存序号：以后加状态时，
   旧库里存着的字符串仍然解得出来；序号会错位，把「失败」读成「排队中」这种错最难查；
2. **`headers` 存 JSON，读坏值退化成空表**而不是整条记录失败：丢 header 顶多少了鉴权，
   丢整条会让用户看到「下载记录凭空少了一条」；
3. **恢复时把 `running` 降级成 `waiting`**（`recoveredStatus`）：上次没跑完就被杀掉的任务，
   库里会留着 `running`。不降级的话它会一直占着一个并发位（``DownloadQueue/concurrencyLimit``），
   而且永远没有东西把它推向完成 —— 表现就是「明明只下着一条，第二条永远排队」。
   认不出来的字符串也回落 `waiting`：宁可重排一次，也不留一条谁都不认识、永远不动的记录。

## 三、契约与 M08b 保持一致

`DownloadTaskStore` 不 `throws`（M2 定的契约），失败返回 `false` / 空值并**留痕**
（`GRDBDatabase.failures`，界面与诊断能读）—— 仓库不允许静默失败。

整批写单独一个方法（`save([DownloadTask])`）：「整部下载」一次加十几条，
逐条写会有十几次事务，还会留下「写了一半」的中间态。

## 四、清单（各自独立）

1. **AppModel 接线**：`downloadTaskStore` 属性 + 加载/写入路径（等传输层有东西可写时一起做，
   否则就是一个没人写的库）；
2. **传输**：分片下载（HLS 按清单展开）+ 断点续传，调度用 ``DownloadQueue``；
3. **本地地址接管**：已下载的集在详情页改成播本地文件；
4. **界面**：详情页的下载按钮 + 「下载管理」的任务列表。

## 五、留口
