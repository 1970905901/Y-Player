# M10k 加密 HLS 下载（AES-128）

- 状态：**已实现**（本地静态闸门全绿 + 新单测；Mac 编译 / 测试待 YG）
- 时间：2026-10-10
- 触发：M10c 的「留口」第一条 —— 加密片段（AES-128）以前**如实拒绝**
  （「这条是加密清单（AES-128），本平台暂不支持下载」）。可真源里 AES-128 的 HLS 很常见：
  拒绝 = 这一集根本下不了。

## 一、做法

1. **解析不改语义，只把事实留下**（`HLSManifest.SegmentKey` + `segmentKeys`，与 `segments` 一一对应）：
   `METHOD` / `URI`（绝对化）/ `IV`。`#EXT-X-KEY` 的作用范围就是「到下一段 KEY 之前」——
   密钥中途轮换跟着换。**IV 缺省时按 RFC 8216 兜底成该片段的媒体序号**（16 字节大端）：
   这要求跟踪 `#EXT-X-MEDIA-SEQUENCE` 与片段计数；`#EXT-X-MAP` 的 init 片**不吃序号、也不带 KEY**。
   为什么按片段存：解密方（`DownloadRunner`）手里只有「第几片」，让它再推一遍序号 = 把解析器的知识抄一遍。
2. **解密**（`AES128CBC`，Core 的 `Support`）：AES-128-CBC + PKCS7，`CommonCrypto` 的 `CCCrypt`。
   密钥 / IV 长度不对、数据不是块长整数倍都给 nil，调用方**如实报错**（不猜、不静默产出）。
3. **下载链路**（`DownloadRunner`）：密钥按 URI 缓存（同一份清单同一把 key 只取一次，key 请求带同一套 header）、
   每片解密后再追加写；**任何一步不对就直接报错**，绝不把密文写进成品。
4. **`isDownloadable` 的口径改了**：字节范围仍不支持；加密**只认 `AES-128`** ——
   `SAMPLE-AES`（要另一套取样规范）继续如实拒绝，理由里点名 SAMPLE-AES。

## 二、口径与取舍

- **密钥请求走既有的 `fetch`**：站点鉴权挂在 header 上的源，key 也多半要；
- **不落盘密钥**：只在这一次执行的字典里缓存，进程结束即无 —— 不做密钥持久化（频次极低，落盘只增加泄漏面）；
- **「解出来对不对」由测试钉住**：夹具用 `AES128CBC.encrypt` 造密文（与解密同一套参数），
  断言落盘字节 == 明文拼接 —— 否则「能下」不等于「下对」。

## 三、故意没做

- SAMPLE-AES / Widevine / PlayReady：Apple 平台没有对应 CDM（SAMPLE-AES 要自研取样解密，另起一轮）；
- 断点续下：仍与 M10d 一样「失败从头下」（续传要对账已完成片段，是另一件事）；
- 加密与字节范围**同时**出现的清单：两条都会拒，理由分开说（范围那条先报）。

## 四、验证点（Mac）

1. `swift test --package-path Packages/CatVodCore`：清单解析新用例 ——
   带 IV 的 key 存成片段信息、缺省 IV = 媒体序号（含中途换 key）、init 片不吃序号、
   SAMPLE-AES 标成「不可下」；
2. `swift test --package-path Packages/CatVodSource`：下载器端到端 ——
   夹具造两片密文，跑完断言文件 = 明文拼接、且 key 只请求一次；外加 SAMPLE-AES 的拒绝用例；
3. 全包测试 + App 编译照旧（**加了一个文件**，跑之前 `rm -rf Packages/*/.build`）；
4. **上机**：找一个 AES-128 的 HLS 源（清单里有 `#EXT-X-KEY:METHOD=AES-128`）下一集 ——
   以前立刻失败，现在应能下完并本地播。

## 五、教训（写给下一次）

- 「先如实拒绝、把事实解析出来」是对的中间态：M10c 只标 `isEncrypted`，让下载器拒绝得干净；
  真要做时先把「谁在什么时候需要什么信息」想清楚 —— 这次差点让下载器自己算 IV（那要把序号知识抄一份）；
- `CommonCrypto` 在 SwiftPM 里 `import CommonCrypto` 就能用（Apple 平台 SDK 自带模块），
  不用引三方加密库。

## 六、留给后面的
