# M04P17 时钟跟着帧走（饥饿看门狗）

- 状态：**已实现**（本地静态闸门全绿 + 新单测；Mac 编译 / 测试待 YG）
- 时间：2026-10-10
- 触发：自研内核的时钟是 `AVSampleBufferRenderSynchronizer` 那条 —— **按墙钟走**。
  读包 / 解码跟不上时它不会等：恢复后那批帧的 pts 全落在时钟后面，显示层按规矩当「迟到帧」丢掉 ——
  用户看到的是「卡一下，然后画面突然快进一段」。网络慢 / 掉线（阻塞读）时更明显。

## 一、做法

1. **纯逻辑**（`FeedStarvationWatchdog`，可单测）：喂「时钟 + 最后一帧 pts」，吐两个边沿
   （刚跨入饥饿 / 刚从饥饿出来），其余什么都不管。阈值 **0.3s** —— 正常播放的点滴抖动不该报缓冲，
   真卡住时也足够小（用户看到的是「停一下」而不是「跳一段」）。
2. **看门狗线程**（0.2s 一次心跳）：解码线程可能正卡在一次阻塞读里，自己报不出来 —— 只能从外面看。
   这条线程只做三件事：读锁里的状态 → 判饥饿 → `videoRenderer.pause()` + 报 `.buffering`。
3. **恢复由解码线程做**：喂帧时记下 pts，若刚才在饿就 `play(rate:)` + 报 `.playing` —— 把表接回去。
4. **界面不用改**：`.buffering` 是早就约定好的状态，弹幕 / 字幕的时钟本来就按它停表
   （`PlaybackClock` 既有口径）；进度条也不动 —— 时钟停着，`timeChanged` 报的就是停住的位置。

## 二、口径与已知取舍

- 这套只治「时钟跑过头」，不治**阻塞读本身**：`av_read_frame` 卡住时我们只能等它返回
  （超时 / `rw_timeout` / `reconnect` 是另一件事，等真遇到再说 —— 动了会波及「现在能播的源」）。
- 判定输入是「最后一帧 pts」，所以**软解 4K 这类解码比实时慢**的场景也会触发 ——
  这正是想要的：表跟着解码速度走，音画不散；代价是播放速度低于 1x（软解本来就是兼容路线）。

## 三、故意没做

- 网络读的 `rw_timeout` / `reconnect` 选项；
- 缓冲进度（`buffered` 事件一直报的是位置，没有报「缓了多少」）；
- 内嵌字幕轨。

## 四、验证点（Mac）

1. `swift test --package-path Packages/CatVodPlayer`：新套件「饥饿看门狗」3 条
   （边沿只报一次 / 慢但一直在出帧不算饿 / 阈值可调）；
2. 全包测试 + App 编译照旧；
3. 上机：本地片子看不出差别（解码跟得上）；软解 4K 或网络慢的源上，卡的时候应该显示
   「缓冲中」、进度停住，恢复后接着放（不再是「卡完跳一段」）。

## 五、教训（写给下一次）

- **mutating 方法不能直接摆在 `#expect` 里**：Swift Testing 的宏展开会把子表达式包进 `$0` 闭包，
  当场报「cannot use mutating member on immutable value: '$0' is immutable」。
  看门狗的状态机就是 mutating（`tick` / `noteFeed`），第一版十条断言一起红 ——
  一律先落局部 `let` 再断言（与「宏里别放复杂表达式」是同一条纪律，见交接文档的坑列表）。
